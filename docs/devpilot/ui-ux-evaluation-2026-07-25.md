# Devpilot 平台交互合理性与信息完整性评估报告

> **评估标识**
> - 评估工具: QoderWork (AI Agent + Chrome Computer Use + 源码静态分析)
> - 评估时间: 2026-07-25 02:49 CST
> - 评估基线: `apps/devpilot-web` (Next.js 15) + `apps/devpilot-api` (NestJS 10) 当前运行态
> - 评估方法: 浏览器实际操作体验 (localhost:3120) + 前端源码全量分析 (21 页面) + 竞品调研 (10 平台)
> - 竞品参考: Vercel, Railway, Render, Fly.io, AWS Console, Portainer, Grafana, Backstage, ArgoCD, Coolify
> - 前置审计: 本报告基于 2026-07-21 六批次修复后的当前状态，不重复已修复问题

---

## 一、总体评价

Devpilot 作为一个覆盖「项目初始化 → 资源管控 → 部署执行 → 运维监控 → 治理审计」全生命周期的研发管控平台，功能覆盖面非常广（33 个后端模块、39 个数据模型、21+ 前端页面）。经过 7 月 21 日的六批次修复后，基础可用性已得到保障（统一反馈体系、状态标签、面包屑、导航重组等）。

但从一个**真实日常使用者**的角度来看，平台当前存在三个层面的核心问题：

1. **信息架构层面**：功能分区过多且边界模糊，用户在 20+ 导航项中难以建立心智模型
2. **操作效率层面**：核心高频操作（部署、查看状态）路径过深，缺乏"一屏总览"能力
3. **信息密度层面**：部分页面信息过载（按钮墙、指标卡堆砌），部分页面信息不足（缺乏上下文关联）

## 二、全局交互评估

### 2.1 导航与信息架构

**当前状态**：侧边栏 8 个分区（仪表盘/项目/基础设施/资源/运维/治理/配置/团队/帮助），共 20+ 导航项，全部平铺展示。

**问题**：

| # | 问题描述 | 影响 | 竞品对比 |
|---|---------|------|---------|
| N-1 | 导航项过多且全部平铺，无折叠/收起机制，视觉扫描成本高 | 新用户迷失，老用户效率低 | Vercel 仅 4 项主导航 + 项目内二级导航；Railway 用 Canvas 拓扑替代列表 |
| N-2 | "资源"分区含 5 个子项（运行态资源/资源申请/资源交付实例/资源连接/密钥中心），术语区分度低 | 用户分不清"资源连接"vs"运行态资源"vs"资源交付实例" | AWS 用统一的 Resource Groups + 类型筛选；Backstage 用 Catalog 统一入口 |
| N-3 | "治理"分区含 5 个子项，对非管理员角色信息过载 | 普通开发者被治理概念干扰 | ArgoCD 将治理内嵌到 App 设置中，不独立暴露；Grafana 将 Alert 规则内嵌到 Dashboard |
| N-4 | 侧边栏搜索仅支持菜单名搜索，不支持项目/服务器/资源等实体搜索 | 无法快速定位目标实体 | Backstage 全局搜索覆盖所有实体类型；Vercel 支持 Cmd+K 全局命令面板 |
| N-5 | 团队切换器 (Test Org) 位于 Header 左上角，但切换后的作用域影响不明确 | 用户不确定当前操作属于哪个团队上下文 | Railway/Coolify 在页面顶部明确显示当前 Team/Project 上下文 |

**改进预期**：

- 将导航收敛为 4-5 个一级入口（概览/项目/基础设施/资源/运维），治理和配置作为二级或设置入口
- 引入 Cmd+K 全局命令面板，支持实体搜索 + 快捷操作（参考 Vercel/Backstage）
- 资源分区合并为统一"资源中心"，用 Tab 或筛选器区分子类型
- 治理功能按角色渐进暴露：普通成员仅见审批入口，管理员见完整治理面板

### 2.2 全局布局与响应式

**当前状态**：Header (Logo + 团队切换 + 创建项目 + 用户信息) + 固定侧边栏 + 主内容区。

| # | 问题描述 | 影响 | 竞品对比 |
|---|---------|------|---------|
| L-1 | Header 同时承载 Logo、团队切换、创建项目按钮、用户名、退出按钮，信息层次不清 | 视觉噪音，创建项目按钮与退出按钮视觉权重相近 | Vercel Header 仅 Logo + 搜索 + 用户头像；操作按钮在内容区 |
| L-2 | 移动端仍为 Header 折叠面板，25 项塞入 grid-cols-2 下拉（已知遗留） | 移动端几乎不可用 | 所有主流平台均有独立的移动端适配或 PWA |
| L-3 | 无全局错误边界/网络断开提示 | API 失败时用户无感知 | Grafana 有全局连接状态指示器 |

### 2.3 反馈与状态系统

**当前状态**：已统一为 sonner toast + ConfirmDialog + StatusTag + ErrorBanner 体系（7/21 修复后）。

| # | 问题描述 | 影响 | 竞品对比 |
|---|---------|------|---------|
| F-1 | 操作成功/失败仅有 toast 一闪而过，无持久化的操作历史入口 | 用户错过 toast 后无法回溯操作结果 | ArgoCD 每个操作都记录为 Event，可在 App 详情中回溯 |
| F-2 | 异步操作（部署、同步、供给）提交后缺乏全局进度指示 | 用户不知道后台有多少任务在跑 | Vercel 顶部有全局部署进度条；Railway 有 Canvas 上的实时状态动画 |
| F-3 | 轮询已实现但无视觉指示（不知道数据是否在自动刷新） | 用户不确定看到的是否是最新数据 | Grafana 有明确的"Last updated"时间戳 + 手动刷新按钮 |

## 三、逐模块交互评估

### 3.1 仪表盘 (/dashboard)

**当前状态**：待处理事项区 + 4 个指标卡（项目总数/进行中部署/待处理资源申请/活跃告警）+ 最近部署列表 + 我的资源申请 + 快捷操作。

**实际体验观察**：
- 最近部署列表显示 6 条完全相同的记录（Picshare · 开发 · blocked · 2026-07-24 10:24），信息冗余严重
- 指标卡仅显示数字，无趋势、无对比、无点击下钻
- 快捷操作仅 3 项（新建项目/申请资源/添加凭证），覆盖面窄

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| D-1 | 最近部署列表无去重/聚合，同一项目的重复 blocked 记录堆砌 | 高 | Vercel 按项目聚合，只显示最新状态 + 时间线 |
| D-2 | 指标卡为静态数字，无趋势图、无环比、无点击跳转 | 中 | Grafana 仪表盘每个面板可交互下钻；AWS CloudWatch 有 sparkline |
| D-3 | 缺乏"系统健康度"总览（服务器在线率、站点可用率、最近告警趋势） | 高 | Coolify 首页显示所有服务的实时健康状态网格 |
| D-4 | 快捷操作固定 3 项，不支持自定义或基于上下文的智能推荐 | 低 | Backstage 首页支持自定义 Widget 布局 |
| D-5 | 待处理事项为空时仅显示"暂无待处理事项，一切正常"，缺乏引导性 | 低 | Railway 空态引导用户创建第一个项目 |
| D-6 | 无时间维度筛选（今天/本周/本月的部署统计） | 中 | Vercel Analytics 支持时间范围选择 |

**改进预期**：
- 部署列表按项目聚合，显示"项目名 · 环境 · 最新状态 · 最近 N 次成功/失败比"
- 指标卡增加 sparkline 趋势 + 点击跳转到对应列表页
- 增加"基础设施健康"区块：服务器在线状态、站点 TLS 到期预警、资源使用率
- 支持用户自定义仪表盘 Widget（参考 Grafana/Backstage）

### 3.2 项目管理 (/projects)

**当前状态**：项目卡片网格（名称/标签/描述/创建日期/Git 关联），支持创建（5 步向导）和导入。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| P-1 | 项目列表无搜索、无筛选、无排序、无分页 | 高 | Vercel 支持按名称搜索 + 按时间排序；Backstage 有完整的 Catalog 筛选体系 |
| P-2 | 项目卡片信息密度不足：无最近部署状态、无环境健康度、无团队成员 | 高 | Vercel 项目卡显示最近部署状态 + 预览 URL；Coolify 显示服务运行状态 |
| P-3 | 项目详情页面包屑显示截断的 ID（cmrwxl1k…）而非项目名 | 中 | 所有竞品面包屑均显示人类可读名称 |
| P-4 | 项目状态"异常"无解释：为什么异常？哪个环节异常？如何修复？ | 高 | ArgoCD 的 Degraded 状态附带具体原因 + 受影响的资源树 |
| P-5 | 创建向导 5 步流程过长，且步骤间无进度保存 | 中 | Railway 创建服务仅需选模板 → 命名 → 部署（3 步）；Vercel 导入 Git 仓库即完成 |
| P-6 | 项目详情页 Tab 结构（概览/部署/环境/Webhook/资源/设置）中，"部署"Tab 与侧边栏"应用服务"功能重叠 | 中 | Vercel 项目详情只有 Deployments/Settings/Analytics/Speed Insights，职责清晰 |

**改进预期**：
- 项目卡片增加"最近部署状态指示灯 + 环境健康摘要"
- 项目状态异常时显示具体原因链（如：部署阻塞 → 执行策略拦截 → 需要审批）
- 面包屑显示项目名称而非 ID
- 创建流程支持"快速创建"（仅名称 + Git 仓库）和"完整向导"两种模式

### 3.3 项目详情 (/projects/[id])

**当前状态**：Header（项目名 + 状态 + Git URL + 创建时间 + 应用/环境计数）+ 6 个 Tab。

**实际体验观察**：
- 概览 Tab：最近部署（单条 + 查看错误按钮）+ 关联应用（服务列表）+ 环境列表（4 个环境卡片）
- 部署 Tab：部署运行列表，每条显示来源/分支/环境/操作人/状态/时间 + 部署变量折叠
- 环境卡片显示"1 服务器 · 2 实例 · 0 站点 · 16 部署"，信息聚合度好

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| PD-1 | 部署列表无筛选（按环境/状态/操作人/时间），16 条记录已需"查看全部" | 高 | Vercel 部署列表支持按分支/环境/状态筛选 + 无限滚动 |
| PD-2 | 部署记录缺乏关键信息：无 commit hash、无部署耗时、无变更 diff 链接 | 高 | Vercel 每条部署显示 commit message + author + 变更文件数 + 部署耗时 |
| PD-3 | "部署变量"折叠面板是唯一的调试入口，缺乏日志/输出查看 | 高 | ArgoCD 部署详情有完整的 Sync 日志 + 资源树 + 事件时间线 |
| PD-4 | 环境卡片无快捷操作（如：一键部署到该环境、查看该环境日志） | 中 | Coolify 环境卡片有 Start/Stop/Redeploy 快捷按钮 |
| PD-5 | 概览 Tab 的"最近部署"仅显示 1 条，与部署 Tab 的完整列表信息重复且不一致 | 低 | 统一为一个入口，概览用时间线展示最近 3-5 条 |
| PD-6 | 项目 Header 的"部署应用"按钮跳转到应用服务页（带 projectId 过滤），而非直接在项目内操作 | 中 | Vercel 项目内直接有 Redeploy 按钮，无需跳转 |

### 3.4 应用服务 (/applications)

**当前状态**：5 个指标卡 + 应用卡片列表（含服务行）+ 创建应用/添加服务弹窗 + 部署向导。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| A-1 | 应用与项目的关系不直观：应用是项目的子集还是独立实体？用户心智模型混乱 | 高 | Vercel 中 Project = Application，无额外抽象层；Railway 用 Project 包含 Service |
| A-2 | 服务行操作按钮过多（部署/重启/回滚/日志/监控/审批等），按钮墙问题（7/21 修复后收敛但仍密集） | 中 | Coolify 服务行仅 Start/Stop/Redeploy 三个主操作，其余收入 ⋯ 菜单 |
| A-3 | 部署向导（DeployWizardHost）多步骤流程缺乏预览/确认环节 | 中 | ArgoCD Sync 前有完整的变更预览（哪些资源会被更新） |
| A-4 | "排队部署运行"和"排队服务操作"复选框的语义不清晰 | 中 | 应明确说明：勾选后操作将进入执行队列等待调度，而非立即执行 |
| A-5 | 指标卡（应用数/服务数/环境数/部署数/操作数）为全局统计，缺乏"当前项目"上下文 | 低 | 应跟随 URL 的 projectId 过滤显示对应项目的统计 |

### 3.5 服务器管理 (/servers)

**当前状态**：服务器卡片网格 + 添加服务器弹窗 + 测试连接 + 详情页。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| S-1 | 服务器卡片缺乏实时状态：CPU/内存/磁盘使用率、在线时长、最近连接时间 | 高 | Portainer 显示容器/主机的实时资源使用率；Coolify 显示服务器 CPU/RAM 实时数据 |
| S-2 | 添加服务器需要手动填写 SSH 凭证，无密钥对生成/导入引导 | 中 | Coolify 支持一键生成密钥对 + 复制公钥引导；Railway 通过 Agent 自动注册 |
| S-3 | 测试连接仅返回成功/失败，无诊断信息（如：DNS 解析失败/端口不通/认证失败） | 中 | Portainer 连接失败时显示具体错误原因 |
| S-4 | 服务器详情页缺乏"该服务器上运行了什么"的总览（站点、容器、服务） | 高 | Portainer 主机详情显示所有容器列表 + 资源使用图表 |
| S-5 | 无批量操作能力（批量测试连接、批量同步） | 低 | Portainer 支持多选批量操作 |

### 3.6 站点管理 (/sites)

**当前状态**：站点列表 + 聚焦面板（URL 参数定位）+ 添加/编辑弹窗 + 生产操作确认。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| ST-1 | 站点卡片按钮过多（同步/TLS 续签/回滚/诊断/冒烟检查等），7/21 修复后仍有 10+ 操作 | 高 | Vercel Domain 设置仅 Show/Remove/Verify 三个操作；Nginx Proxy Manager 每站点仅编辑/删除 |
| ST-2 | 站点状态缺乏可视化：TLS 证书到期时间、最近同步时间、响应时间等关键运维指标不可见 | 高 | Coolify 显示 SSL 状态 + 到期天数；UptimeRobot 显示响应时间曲线 |
| ST-3 | "排队站点操作"复选框语义同 A-4，用户不理解"排队"的含义 | 中 | 应改为"维护模式"或"批量操作模式"等更直观的命名 |
| ST-4 | 聚焦面板（FocusedSitePanel）通过 URL 参数定位，但无明确的视觉指示说明当前聚焦了哪个站点 | 中 | 应有高亮边框或面包屑明确标识 |
| ST-5 | 站点与服务器、项目、环境的关联关系在列表中不可见 | 中 | 应在站点卡片上显示"所属项目 · 环境 · 服务器"标签 |

### 3.7 资源管理（运行态/申请/实例/连接/密钥）

**当前状态**：5 个独立页面分别管理资源的不同生命周期阶段。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| R-1 | 资源生命周期被割裂为 5 个页面，用户需要在多个页面间跳转才能理解一个资源的完整状态 | 高 | AWS 资源详情页有统一的"生命周期事件"时间线；Backstage 用 Catalog 实体统一展示 |
| R-2 | "运行态资源"页面名称晦涩，实际是 Docker 容器/云资源的纳管面板 | 中 | 应改为"基础设施资源"或"托管资源"，与侧边栏"资源"分区名区分 |
| R-3 | 资源申请流程（创建→审批→供给→实例）跨 3 个页面，无统一的流程可视化 | 高 | AWS Service Catalog 有统一的"请求状态追踪"页面，显示完整流程进度 |
| R-4 | 资源交付实例页的 delivery 字段用 CodeBlock 展示原始 JSON，对非技术用户不友好 | 中 | 应结构化展示（如：连接地址/端口/用户名/密码分字段显示，密码可复制） |
| R-5 | 密钥中心的"生成密钥"和"存储密钥"两个入口的关系不清晰 | 低 | 应合并为一个流程：生成 → 自动填充 → 存储，或明确说明"存储"用于导入已有密钥 |
| R-6 | 资源连接页（/resources）信息过简：仅名称 + 类型，无连接状态、无最近使用时间 | 中 | 应显示连接测试结果、最近使用的项目、创建时间 |

### 3.8 监控告警 (/monitoring)

**当前状态**：仪表盘面板（资源指标 + SLO）+ 4 个 Tab（告警事件/规则/静默/通知渠道）+ 时间窗口切换。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| M-1 | 资源指标面板无实际图表，仅显示"资源类型/指标来源/状态/样本数"元数据 | 高 | Grafana 有完整的时序图表 + 阈值线 + 注解；AWS CloudWatch 有交互式图表 |
| M-2 | 时间窗口切换器（15m/1h/6h/24h）存在但无对应的时序数据展示 | 高 | 时间窗口应控制图表的显示范围，而非仅影响列表 |
| M-3 | 告警规则创建弹窗（CreateRuleModal）存在但缺乏模板/预设 | 中 | Grafana 提供告警规则模板 + 基于 Label 的路由；PagerDuty 有预置规则库 |
| M-4 | SLO 面板仅显示服务名 + 数值，无目标线、无错误预算消耗、无趋势 | 高 | Grafana SLO 面板有目标线 + 错误预算燃烧率 + 30 天趋势 |
| M-5 | 告警事件缺乏关联上下文：触发时的指标快照、影响的服务、相关的部署事件 | 中 | PagerDuty 告警附带时间线（最近部署 + 指标异常 + 相关变更） |
| M-6 | 通知渠道配置缺乏"测试发送"能力 | 低 | Grafana 通知渠道有"Send Test Notification"按钮 |

### 3.9 日志中心 (/logs)

**当前状态**：左右分栏（日志流侧边栏 + 日志查看器）+ 工具栏（搜索/过滤）+ 新建流弹窗 + SSE 实时推送。

| # | 问题描述 | 严重度 | 竞品对比 |
|---|---------|--------|---------|
| LG-1 | 日志查看器缺乏语法高亮和结构化解析（JSON 日志应自动格式化） | 中 | Datadog 自动解析 JSON 日志为结构化字段；Grafana Loki 有 LogQL + JSON 展开 |
| LG-2 | 无日志级别（ERROR/WARN/INFO）的视觉区分和快速筛选 | 高 | 所有主流日志工具都有级别着色 + 一键筛选 |

| LG-4 | 日志流侧边栏无搜索/分组能力，流数量增多后难以定位 | 低 | Grafana 日志流支持按 Label 分组 + 搜索 |
| LG-5 | SSE 实时推送无暂停/恢复控制，大量日志时页面可能卡顿 | 中 | Datadog Live Tail 有暂停按钮 + 自动滚动锁定 |

### 3.10 备份管理 (/backups)

**当前状态**：4 个指标卡 + 备份计划卡片列表（左）+ 运行记录列表（右）+ 创建计划弹窗。

| B-2 | 备份计划缺乏调度可视化：下次执行时间、执行频率、保留策略 | 中 | AWS Backup 有清晰的调度表达式 + 下次运行时间 + 保留规则 |

## 四、核心操作链路评估

### 4.1 部署链路（最高频操作）

**当前路径**：项目详情 → 部署应用（跳转应用服务页）→ 选择服务 → 部署向导 → 确认 → 等待执行

**问题**：
- 需要 2 次页面跳转才能触发部署（项目 → 应用服务 → 向导）
- 部署后需要手动刷新或等待轮询才能看到状态变化
- 部署失败后缺乏"一键重试"和"查看失败原因"的快捷入口
- 无部署对比能力（本次部署 vs 上次部署的变更）

**竞品最佳实践**：
- Vercel：git push 即部署，零操作；手动部署仅需 1 次点击（Redeploy）
- ArgoCD：Sync 按钮 + 变更预览 + 一键回滚，全在同一页面
- Coolify：服务卡片上直接有 Redeploy 按钮

**改进预期**：
- 项目详情页增加"快速部署"按钮（选择环境 → 确认 → 执行），无需跳转
- 部署记录增加"重试"和"回滚到此版本"操作
- 部署详情页增加日志流 + 步骤时间线 + 变更 diff

### 4.2 资源申请链路

**当前路径**：资源申请页 → 创建申请 → 选择类型/项目 → 提交 → 等待审批 → 审批通过 → 供给执行 → 实例交付

**问题**：
- 申请创建后，用户需要分别访问"资源申请"和"资源交付实例"两个页面追踪进度
- 审批人缺乏上下文：不知道这个资源是给哪个项目用的、预期规格是什么
- 供给失败后缺乏明确的错误信息和重试引导

**竞品最佳实践**：
- AWS Service Catalog：统一的"请求追踪"页面，显示完整流程状态机
- Backstage Software Templates：模板化申请 + 自动化供给 + 统一状态追踪

**改进预期**：
- 资源申请详情页增加"流程时间线"（申请 → 审批 → 供给 → 交付），每个节点显示状态和时间
- 审批卡片增加项目上下文（项目名称、用途说明、预期规格）
- 供给失败时显示具体错误 + 建议操作（重试/修改参数/联系管理员）

### 4.3 故障排查链路

**当前路径**：仪表盘（发现异常）→ 项目详情（查看部署状态）→ 应用服务（查看服务状态）→ 日志中心（查看日志）→ 监控告警（查看指标）

**问题**：
- 排查一个故障需要跨越 4-5 个页面，每次都需要重新选择上下文（项目/环境/服务）
- 各页面之间缺乏"关联跳转"（如：从告警事件跳转到对应服务的日志）
- 无"故障时间线"概念（将部署事件 + 告警事件 + 日志异常按时间排列）

**竞品最佳实践**：
- Datadog：从告警 → 指标 → 日志 → Trace 全链路关联，一键跳转
- Grafana：Dashboard 面板可配置 Data Link，点击指标异常直接跳转到对应日志
- ArgoCD：App 详情页有统一的 Events + Logs + Resources 三合一视图

**改进预期**：
- 引入"服务健康"聚合视图：在一个页面内显示服务的部署状态 + 最近告警 + 日志尾部 + 资源使用
- 告警事件卡片增加"查看相关日志"和"查看最近部署"快捷链接
- 项目详情概览 Tab 增加"最近事件时间线"（部署 + 告警 + 操作审批按时间排列）

## 六、竞品交互模式借鉴总结

### 6.1 最值得借鉴的交互模式

| 模式 | 来源 | 适用场景 | 实现建议 |
|------|------|---------|---------|
| Deploy = URL | Vercel | 每次部署生成唯一预览链接 | 部署记录增加预览 URL（即使是内部环境） |
| 即时回滚 | Vercel/Render | 无需重新构建即可回滚 | 部署历史中增加"回滚到此版本"一键操作 |
| Canvas 拓扑 | Railway | 可视化服务间依赖关系 | 应用详情页增加服务拓扑图 |
| 双状态模型 | ArgoCD | Sync 状态 + Health 状态分离 | 服务状态拆分为"部署状态"和"运行健康度" |
| Label 路由 | Grafana | 告警规则与通知渠道解耦 | 告警规则打标签 → 通知策略按标签路由 |
| 全局命令面板 | Vercel/Backstage | Cmd+K 快速搜索和操作 | 引入全局搜索 + 快捷操作面板 |
| 渐进式配置 | Railway/Coolify | 零配置默认 + 折叠高级选项 | 创建表单默认最简，高级选项折叠 |
| 事件时间线 | ArgoCD/Datadog | 统一展示所有变更和异常 | 项目/服务详情增加事件时间线 |

### 6.2 信息密度最佳实践

竞品普遍采用四层信息递进模式：

1. **概览层**（3-5 个关键指标）：仪表盘/项目卡片
2. **列表层**（可筛选表格）：部署列表/资源列表
3. **详情层**（完整配置 + 日志 + 指标）：项目详情/服务详情
4. **诊断层**（diff/树/关联分析）：部署对比/故障排查

Devpilot 当前的问题是各层之间的边界不清晰：仪表盘信息太少（仅数字），列表页信息太多（按钮墙），详情页信息不够（缺乏日志/指标/diff）。

## 九、评估方法说明

本次评估采用三种方法交叉验证：

1. **浏览器实际操作**：通过 Chrome Computer Use 工具实际访问 localhost:3120，获取仪表盘、项目详情等页面的完整可访问性树（Accessibility Tree），验证实际渲染内容和交互元素
2. **源码静态分析**：通过 AI Agent 全量阅读 21 个前端页面的 page.tsx 及其组件导入，分析每个页面的数据展示、操作按钮、表单弹窗、空态/错误态处理
3. **竞品对比调研**：通过 AI Agent 调研 10 个主流研发部署平台的交互设计模式，提取可借鉴的最佳实践

评估视角为"日常使用该平台进行项目部署和运维的开发者"，重点关注操作效率、信息可获取性、错误恢复能力三个维度。
