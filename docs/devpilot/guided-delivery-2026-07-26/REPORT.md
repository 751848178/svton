## 一、结论

本次已经把“项目、环境、资源、应用、部署”从分散功能入口重组为一条
新用户能从项目首页直接理解和继续执行的交付路径：

> 创建项目管控条目 → 确认仓库/解析事实 → 准备项目环境 → 申请并关联资源
> → 准备应用服务 → 生成计划 → 审批/执行 → 查看完整证据

流程中的关键误导已被修正：

- 手工填写仓库信息不再被表述为自动导入或解析。
- 资源申请会携带真实项目环境，而不是只保存一个无法关联的环境文本。
- 原“关联到环境”不会再只做预览却提示成功；现在必须预览、输入环境名
  二次确认，再以真实应用模式提交并回读结果。
- 部署演练明确表示“不连接目标、不执行命令”；演练成功不会再把项目健康
  误判为正式部署健康。
- 部署记录不再只有状态和时间，能够展开查看目标、环境、应用、服务、
  服务器、审批、执行任务、脱敏命令/变量、错误、日志和结果。

当前结果可作为真实控制面的第一层产品闭环，但不能宣称已经具备自动仓库
扫描、外部生产部署验收或 provider 侧资源完整回收能力。

## 二、调研所得的最优交互原则

子代理对 Railway、Render、Vercel、Heroku、GitLab 和 Harness 的官方产品
文档与交付路径进行了对照。最终采用的共同原则如下：

1. **一个项目首页、一条主路径、一个推荐动作。**  
   用户不应先理解平台菜单结构，首页应直接告诉他当前缺什么和下一步做什么。

2. **Project / Environment 是资源和权限的归属边界。**  
   资源申请、实例、应用、服务和部署都必须指向真实环境 ID，避免只显示
   `dev` 文本却无法用于后续注入或治理。

3. **解析结果、待发布变更、审批和执行是不同事实。**  
   “已配置”“已生成计划”“已批准”“已执行”“已验证”不能合并为一个成功状态。

4. **变更前预览影响，变更后回读结果。**  
   对资源关联、部署等有副作用的动作，需要明确变更对象、目标环境、
   命令/变量和风险，并保留可追溯证据。

5. **详情页必须自带诊断信息和下一步。**  
   状态标签本身不能帮助用户排障；必须同时给出原因、门禁、错误、
   计划、日志、结果和可执行的下一动作。

## 三、优化后的完整流程

| 阶段 | 新手看到什么 | 主操作 | 完整证据/状态 |
| --- | --- | --- | --- |
| 1. 项目条目 | 项目是否已进入团队管控、采用哪种接入范围 | 创建项目管控条目 | 项目名称、范围、创建时间、仓库声明 |
| 2. 仓库与解析 | 当前是手工配置还是已验证解析 | 完成五步配置检查 | 仓库、分支、技术栈、命令及“未验证”状态 |
| 3. 项目环境 | 哪些环境可用、是否可承载服务和资源 | 创建/查看环境 | 环境 ID、标识、启用状态、服务器/资源/部署计数 |
| 4. 资源申请与关联 | 当前环境已有多少资源、缺什么 | 为当前环境申请资源 | 项目 ID、环境 ID、申请、实例和关联状态 |
| 5. 应用与服务 | 是否存在可部署服务 | 创建/查看应用服务 | 应用、服务、目标服务器、活跃状态 |
| 6. 计划与审批 | 本次是只读计划还是真实部署 | 生成并核对计划 | 命令、工作目录、变量键、目标和风险 |
| 7. 执行与验证 | 审批是否完成、任务是否创建、结果如何 | 查看部署证据 | 审批、任务、错误、日志、结果、时间 |

项目首页按此顺序显示六个准备阶段，并只给一个“建议下一步”。资源申请保留
项目/环境上下文，完成后可返回原项目资源页；项目 Tab 也会保存在 URL 中。

## 四、问题与更好的预期

| 原问题 | 已落地的预期 | 当前结果 |
| --- | --- | --- |
| 新手进入项目后不知道从哪里开始 | 首页显示固定交付路径、完成度、证据和一个推荐动作 | 已完成 |
| “导入项目”像是会扫描仓库，实际只是保存表单 | 明确命名为项目管控条目，并标注手工配置/未验证 | 已完成 |
| 项目接入表单过长、缺少阶段感 | 改为范围、仓库、部署、环境、事实确认五步 | 已完成 |
| 资源申请只带环境文本，无法稳定关联真实环境 | 选择并提交真实项目环境 ID | 已完成 |
| 资源关联按钮只做 dry-run，却提示已经成功 | 预览 → 输入环境名确认 → 真实应用 → 回读结果 | 已完成 |
| 页面默认全选资源，误操作风险高 | 默认不选择，仅显示可关联资源 | 已完成 |
| 资源释放看起来会回收外部资源和凭据 | 改为“标记为已释放”，明确不会执行 provider 回收/吊销 | 已完成 |
| dry-run 文案让人误以为会连接和执行 | 明确“不连接目标服务器，也不会执行命令” | 已完成 |
| dry-run 成功会把项目显示为健康 | 项目健康只采用最近正式部署结果 | 已完成 |
| 部署记录只有摘要，无法诊断 | 展开显示运行语义、目标、审批、任务、命令、变量、日志和结果 | 已完成 |
| 页面状态无法分享/恢复 | 项目 Tab 写入 URL；跨页面入口携带项目/环境/返回地址 | 已完成 |

- 正式部署记录可展开读取目标、环境、应用、服务、服务器、审批、执行任务、
  全部脱敏命令、环境变量键、错误、日志和结果。

## 八、仍需继续补齐

1. **真实只读仓库连接和解析运行。**  
   当前只诚实展示“手工配置、未验证”；下一阶段需要 Git 凭据、仓库连通性、
   commit/branch 证据、解析运行 ID、检测结果和过期状态。

2. **统一项目活动时间线。**  
   当前部署详情已完整展示已有字段，但项目、解析、环境、资源申请、绑定、
   审批和执行还没有统一 Activity read model 与 correlation ID。

3. **资源注入失败必须阻断。**  
   后端仍存在资源环境变量解析失败后降级继续的边界，应改为显式阻断并展示
   缺失资源和错误原因，避免带错误配置进入正式执行。

4. **provider 侧资源释放与凭据吊销。**  
   目前释放动作只更新平台数据库状态；UI 已消除误导，但外部资源回收、
   连接终止、凭据吊销、回收日志和失败补偿仍需实现。

5. **正式生产验收。**  
   本次仅验证本地真实控制面和只读计划，没有使用真实云账号、外部生产服务器
   或真实 provider，因此不能作为生产签收。

## 九、建议下一阶段验收标准

- 仓库连接后产生可追踪的分析运行，包含 commit SHA、检测器版本、时间、
  结果、错误和重试。
- 所有项目活动共享 correlation ID，可从项目首页追到申请、审批、执行和日志。
- 缺失/失效资源在计划阶段阻断，不能静默降级。
- 资源释放能够回收 provider/pool、吊销凭据并保存每一步结果。
- 使用一次可控的外部测试环境完成正式部署、健康检查、回滚和证据复核。
