# Svton Agent / Codex Desktop UI And Interaction Parity

## Goal

Make the non-Devpilot svton agent desktop and web experience behave coherently with the current Codex Desktop experience, based on current source mapping, direct operation of both products, screenshot-backed comparison, implementation, runtime verification, and independent review.

## Scope

- In scope: `ai/agent-client`, `ai/agent-ui`, `ai/agent-app`, `apps/agent-web`, `apps/agent-desktop`, and directly related agent contracts/tests.
- In scope: session navigation, conversation lifecycle, message/content blocks, streaming and process states, tools/approvals/questions, results/artifacts, composer behavior, background sessions, errors/recovery, settings, desktop shell behavior, accessibility, and visual consistency.
- In scope: current Codex Desktop as the reference surface, with current-run screenshots and interaction observations as audit evidence.
- Out of scope: Devpilot server-agent/task-pull/deployment surfaces unless source tracing proves that a shared agent UI contract requires a bounded change.
- Out of scope: unrelated dirty worktree changes and speculative feature additions that Codex Desktop does not substantiate.

## Clarifications And Assumptions

- Confirmed: research and implementation are delegated in phases, with one active writer in the checkout.
- Confirmed: potential AskUserQuestion decisions first receive an independent adversarial subagent review; user input is requested only for a remaining material blocker.
- Confirmed: implementation is followed by a draft MR, deep code review, issue-specific investigation, architect reconciliation, final fixes, commit, and push.
- Assumption: "MR before deep review" means an initial implementation commit/push and draft MR, followed by review fixes and a final commit/push.
- Assumption: old audit artifacts are discovery aids only; current-run screenshots and runtime evidence are required for acceptance.

## Workflow Routing

`routing: long-goal + specialized-workflow + noisy-tools; broad cross-module UI/state audit requires invest/impl/review/architect workers, a persistent board, current UI capture, and isolated verification logs.`
