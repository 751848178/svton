# Shipkit 多服务与选择性发布规划

日期：2026-10-04。状态：规划完成，功能尚未实现。路线：todo-plan。

目标：保留现有单镜像用法，让一个项目的一次发布能够构建、推送和更新多个应用服务，也能选择其中部分服务发布；本机和 AI Agent 使用相同的非交互 CLI。

## 当前基线与验收边界

- 当前版本为 0.5.0，原生 `ship release` 处理一个镜像和一个应用服务；已有动态构建机创建、定时销毁及流水线退出时主动释放逻辑。
- `ShipSpec` 支持 Dockerfile、context、buildArgs、ports、envFile、healthcheck，尚无 build target、多服务、外部网络或持久化挂载声明。
- TWGG 已有 backend/admin/mobile 三个应用镜像，以及独立运行的 MySQL、Redis；保留这个结构，不把三个服务拆成三个独立项目。
- 本轮 TWGG 三镜像构建、TCR 推送、运行端 r1 部署已有实测证据；专用 Compose 适配绑定首次部署基线，尚未成为通用连续发布工具。
- H5 React 依赖解析已修源码，但 r2 上线与页面验收未完成。本机原生动态构建模板仍有占位项。
- 两台临时构建机及专用安全组已回读确认释放，运行服务器保持现状。当前工作只规划和保存基线，不恢复生产部署。
- v0.5 的脚本锁、归属隔离、环境快照和安装检查结果属于相应代码范围，不能代替新增多服务的真实环境验收。

## 用户操作契约

以下是拟新增用法，当前版本不可执行 `--services` 或 `--plan`：

```bash
ship release --plan --json
ship release --services admin --plan --json
ship release --services admin --json
ship release --services backend,mobile --json
ship release --json
```

- 默认发布配置中的全部应用服务；MySQL、Redis 等既有基础服务不在默认应用选择中。
- `--services` 接收服务名称，空列表、未知名称和重复名称在创建构建机前明确拒绝。
- 只构建、推送、拉取并更新选中的服务；未选服务保持当前镜像、环境快照、容器及挂载，不因本次发布重启。
- 首次部署没有可继承快照时，必须覆盖所有必需应用服务；缺少任一服务在产生费用前拒绝。
- `--plan` 输出选择、将继承的服务版本、资源绑定及可检查的依赖约束，不创建云资源、不拉镜像、不修改运行状态。
- 计划中使用稳定服务名，不以容易误选的镜像 tag 作为服务身份；镜像实际内容固定到 digest。
- 本期 CLI 保持非交互，支持 `--json` 和确定的退出码；交互式勾选可后续复用相同计划模型，不作为实现前置。

## 规格与兼容

- 引入明确的多服务规格版本（建议 `schemaVersion: 2`），项目名对应发布组，`services` 按稳定名称描述应用。
- 每个服务声明 Dockerfile、context、target、buildArgs、ports、envFile、healthcheck、外部网络和受控挂载。
- 原有单服务 `ship.yaml` 无需修改；内部规范化为一个服务，原有 CLI、归属规则与快照仍可读取。
- 新 CLI 在构建前检查 runtime 的多服务、选择性发布及快照能力；旧 Agent 不支持时拒绝，不静默退化成单镜像部署。
- v1 部署不自动导入或改名。既有业务栈接管须显式核对项目/环境、Compose project、路径、镜像、容器、网络和卷，形成可重复的绑定记录。
- 构建参数的秘密限制继续适用；运行秘密只通过运行端安全通道和私有快照处理，不进入源码包、镜像、公开 manifest 或 JSON 日志。
- 第一阶段限制为 Linux amd64，显式声明和检查镜像架构；不将多架构构建混入本期。

## 构建与版本记录

- 同一临时构建机完成选中服务的构建，第一阶段串行执行；Dockerfile target 必须传入并验证。
- 全部选中服务构建成功后才开始推送；全部 push/digest 校验成功后才产生可部署构建 manifest。中途失败可残留仓库镜像，但不能报告完整构建成功。
- 构建 manifest 记录项目身份、选中服务、各服务镜像 digest、源码提交/补丁摘要、构建规格及架构；不把一个基础提交伪装成所有服务均来自同一版本。
- 运行发布快照记录 `releaseId`、父版本、`changedServices` 和所有应用服务的完整镜像/运行规格组合。
- 未选服务继承当前运行快照及各自源码出处；完整线上组合始终可查询，但继承不代表重新部署。
- 运行环境快照保存在运行端私有目录，导出的 manifest 只含必要的非秘密引用和摘要。
- 发布状态提交与镜像激活之间的故障恢复沿用 v0.5 的保护，并扩展到本次服务集合。

## 运行端部署与恢复

1. 在项目/环境发布锁内核对身份和当前版本，建立不可变的本次计划及前一组快照。
2. 验证全部必需服务、声明的依赖、端口、网络、挂载、所有权和状态可读取性；失败保留现场。
3. 拉取并检查所有选中服务的 digest，再开始切换，避免拉取失败时已有部分服务被停止。
4. 只更新选中应用服务，不执行 Compose down、全局 prune、删卷或未声明的 orphan 清理。
5. 检查所有变更服务及声明的关键联动探针；全部通过后才提交新发布状态。
6. 切换、健康检查或状态提交失败时，恢复本次实际变更服务的前一镜像和运行快照；未选服务保持原状。
7. 首次部署没有旧快照时，明确报告恢复范围及实际现场，不能假报已回到旧版本。
8. 数据库备份、迁移和恢复单独定义；应用镜像回退不自动恢复数据库，也不证明 schema 兼容。

- 同一项目/环境的全量、部分发布和回滚串行，基于锁内最新快照合并；禁止两个部分发布覆盖彼此的状态。
- 同一 Docker daemon 的资源归属必须可核验。既有外部网络/卷只能按显式绑定使用，不自动认领同名资源。
- v1 的同名应用冲突拒绝策略保留；v2 服务资源以项目、环境、服务身份隔离，实际命名规则须有稳定碰撞测试。
- 回滚默认撤销最近一次发布的 `changedServices`；显式服务回滚须有对应历史快照，并以当前版本做冲突检查。
- 回滚形成新的完整发布记录，保留原历史；过期计划、不可读快照或归属变化均拒绝执行。
- 服务依赖检查基于声明的约束和联动测试，不承诺自动推断任意代码/API/database 兼容性；缺关联服务时提示所需集合，不静默扩大选择。

## 基础资源与动态构建

- 第一阶段沿用 TWGG 现有 MySQL、Redis、网络和数据库卷；新增能力只管理应用服务及经核验的应用挂载。
- 第一阶段支持显式外部网络、外部命名卷和受限 bind mount；不开放任意原始 Compose 指令注入。
- 内置能力以通用规格和执行层实现，TWGG 只提供项目配置；不为 deyi、Devpilot 等分别复制发布脚本。
- 填实本机 builder 配置：规格、镜像、VPC/子网、安全组、引导包分发和 Agent 可达入口；沿用私有云/TCR凭据。
- 成功、失败、超时、取消都尝试主动释放构建机；进程中断另由经过回读校验的云端销毁定时器兜底。
- 应用部署成功但构建机释放失败时，分别记录两个结果并明确返回待清理状态；不能因此回滚健康应用，也不能宣称资源已释放。
- 默认无复用；明确指定保留时输出实例身份和释放方法。不得修改或销毁未经身份核验的云资源。
- 生产部署仍暂停。真实 TWGG/按量云验收在用户明确恢复后执行，不从规划文档推导操作授权。

## 分阶段实施与验收

| 阶段 | 交付 | 必须取得的证据 |
| --- | --- | --- |
| MS-01 规格和发布计划 | v1兼容、v2规格、选择解析、只读计划、能力协商 | 非法选择和旧Agent在云创建前拒绝；未选版本正确继承；秘密不进入计划 |
| MS-02 多镜像构建 | target、amd64、同机串行构建、digest manifest | TWGG三个target正确；单服务只构建所选镜像；失败不产生完整manifest |
| MS-03 运行快照与归属 | 完整组合、服务快照、外部资源绑定、锁内合并 | 两个部分发布串行不丢更新；跨项目/环境拒绝越权；坏快照拒绝 |
| MS-04 切换和回滚 | 预拉取、选中服务激活、健康判定、故障恢复 | 注入拉取/切换/健康/状态写入故障；未选容器ID和StartedAt不变 |
| MS-05 原生动态入口 | 配置、引导、推拉凭据和释放闭环 | 本地/隔离测试通过；真实CVM主动删除与定时器回读另行验收 |
| MS-06 TWGG真实验收 | 首次接管、再次全量、只更新admin、应用回滚 | H5页面正常；MySQL/Redis及非目标容器/卷/数据不受影响；临时实例确实不存在 |
| MS-07 文档与推广 | 端点安装、AI Agent命令、deyi等配置示例 | 项目配置代替专用脚本；单镜像原有入口持续通过；能力与验收范围准确 |

每阶段保持一个 active TODO；完成后记录命令、退出码、数量、证据位置和实际边界。source 文件遵循 200 行上限和单一职责，不扩大 TCP 锁修复范围。
