# Shipkit 新手使用体验实施方案

> 日期：2026-09-29。
> 状态：方向已确认，实施待开始。本文持久化用户认可的“安装即用 → 首次向导 → 日常发布”方向；具体接口和字段是待实现设计，不代表当前已支持。
> 范围：当前 Shipkit 工具链的易用性改造。此次仅产出方案，不执行安装、部署、收费资源操作或代码改造。

## 1. 目标与交付边界

让使用者围绕“发布哪个应用、发布到哪里”完成交付。项目识别、配置生成、机器配对、连接检查和结果解释由工具承担。用户无需理解 agent 内部接口、手写 YAML 或从原始日志里猜测部署是否成功。

目标体验：

```text
安装 Shipkit
    ↓
ship init
    选择应用 → 连接服务器 → 连接镜像仓库
    → 完成安装/配对 → 检查 → 保存配置
    ↓
首次发布确认：源码、服务器、应用端口、将产生的变更
    ↓
ship release
    检查 → 准备源码 → 构建 → 推送 → 部署 → 验证
    ↓
显示运行版本、健康结果、业务地址或待完成的访问配置
```

后续在已初始化项目中执行 `ship release` 即可更新；已有用户继续使用 `build/deploy/rollback/status/gc` 等命令。`ship init` 为拟新增命令。

首版支持对象：使用 macOS/Linux 控制器、已有 Linux 服务器和镜像仓库、单个应用、项目已有可用 Dockerfile 的用户。需要一名拥有机器管理权限的人完成首次安装动作；应用使用者可以通过配对码接入管理员已准备好的环境。

“更小白”不意味着用户无需服务器、仓库或权限。首版把已有基础设施变成可引导接入的资源；购买服务器、自动开通仓库、复杂项目适配留给后续扩展。

## 2. 现状与要消除的负担

基线以 [当前使用手册](user-guide.md)、[CLI 入口](../src/cli/main.ts)、[配置校验](../src/shared/config.ts) 和 [初版架构](design.md) 为准。

| 当前负担 | 目标行为 | 完成证据 |
| --- | --- | --- |
| 从仓库编译并定义 shell 函数 | 安装版本化产物后直接运行 `ship` | 干净环境安装验收 |
| 手写两个 YAML | 向导采集少量业务信息，生成并校验配置 | 示例项目无需手写 YAML 完成发布 |
| 搞不清构建机和运行机 | 用“构建应用的机器”“运行应用的服务器”说明用途 | 用户能确认各角色与资源占用 |
| 手工复制长期 token | 使用短期配对凭据连接机器 | 配对成功后长期凭据不出现在命令输出 |
| 配好了 URL，却没配好 TLS/网络 | 检查真实连接，定位需要谁做什么 | 错误入口无法被标记为接入完成 |
| 不知道凭证应该放在哪台机器 | 在向导里填写用途，按角色分发并验证 | builder 能 push、runtime 能 pull |
| 看日志猜成功与失败 | 分阶段进度和明确终态 | 能区分新版成功、旧版恢复、恢复失败 |
| 断线后重新跑命令 | 记录 jobId，恢复查询原任务 | 不重复提交相同部署或清理 |

## 3. 已确定的产品与架构决策

1. **先做好 CLI 向导。** 当前阶段不新增桌面端或 Web 管理平台，避免同时维护两套交互。
2. **首选固定构建机。** 动态腾讯云构建机留在高级模式，在生命周期和 TLS 实机验收完成前不进入新手默认路径。
3. **保留控制器不直接 SSH 的约定。** 首次安装由管理员在目标机执行一条受控命令，或由既有运维系统分发；日常操作仍由 CLI 调用 agent。上一轮讨论中的“自动安装”按此范围落实，不引入隐式 SSH 控制通道。
4. **先支持已有 Dockerfile 的单应用。** 自动检测给出候选与理由，不能识别时清楚说明缺少什么；多服务、数据库迁移、复杂 monorepo 不自动猜测。
5. **现有配置继续可用。** 向导生成配置，不强迫老用户迁移；重跑向导先显示变化，不覆盖已有配置、Dockerfile 或环境文件。
6. **首次配置与日常发布分开。** `init` 默认只完成配置；全部检查通过后可让用户选择首次发布，默认不部署。
7. **结果必须可核实。** 无业务 URL 时不编造地址，健康检查未配置时不展示“应用健康”，客户端超时不展示“服务器已停止”。
8. **授权随具体动作走。** 展示目标和变更后再执行安装、修改入口、发布或删除；已有明确授权且参数未变化时不重复打断。不会用一个全局确认覆盖之后新增的收费或删除范围。

如未来确需控制器直接 SSH 安装，应另写架构决策，明确权限、主机身份验证与兼容影响；本方案不以此作为实施前置条件。

## 4. 首次向导的具体行为

### 4.1 入口与项目识别

在应用目录执行拟新增的 `ship init`。先读取现有 `ship.yaml`、控制器配置和初始化进度，再识别 Dockerfile、项目清单、锁文件、候选端口。

向导第一屏只询问：

```text
准备发布哪个应用？
目录：/projects/demo-web
名称：demo-web
构建方式：已有 Dockerfile
应用端口：3000（检测值，请确认）
健康检查：/health（需要应用真实提供）
```

检测结果必须注明来源。多个 Dockerfile 或多个应用时让用户选择；未知端口、运行命令和健康路径不静默填入可能错误的默认值。

无 Dockerfile 时，首版保存进度并指向受支持的模板说明，不进入假成功状态。后续模板阶段只对明确支持的项目生成可预览文件，并验证真实构建和启动。

### 4.2 连接服务器

先选择“使用已接入机器”或“接入新机器”。用业务语言解释 builder 和 runtime；默认分开选择。已有专用测试机可显式选择同机承担两种角色，先显示构建期间的 CPU、内存和磁盘竞争风险，不默认为生产运行机增加构建负载。

已接入机器：输入 HTTPS 入口和配对凭据，校验证书、身份、角色、agent 版本、Docker/Compose 可用性。

新机器：展示需要的系统条件与安装变更清单，生成一次性接入任务。管理员在目标机执行受控安装命令，安装器完成依赖检查、agent 配置与注册；向导等待并验证接入结果。

安装前明确会写入的目录、服务和监听方式。重装需要识别已有版本与配置，保留有效凭据；现有 `install.sh` 会重写配置，不能直接复用其行为宣称“幂等安装”。

### 4.3 TLS 与安装包分发

首版支持“已有可信 HTTPS 入口”与“管理员按引导配置 Caddy”两条路径。向导可以生成反代配置、检查 DNS/证书和提供复检；修改已存在的 Caddy 站点或网络规则前显示具体差异。DNS 供应商自动接入不作为首版依赖。

安装器与 agent 包都从可信入口获取，分发产物带版本和完整性校验。CLI 必须能检查实际下载地址；仅把外层 curl 地址改成 HTTPS 不算完成。

当前 `serve-bundle` 是临时 HTTP 服务，不能直接作为新手公网分发默认方案。新增分发逻辑必须覆盖外层脚本与内部下载地址，并限制临时服务的监听范围和存活时间。

域名和网络尚未准备好时，向导保存进度，明确显示“等待管理员配置入口”和具体复检动作。不能通过关闭证书验证或开放公网明文端口完成向导。

### 4.4 配对与凭证

配对设计采用 agent 侧创建的随机、高熵、短期一次性凭据，由管理员通过已有可信渠道交给使用者。CLI 先验证 HTTPS 入口，再交换配对凭据；绑定机器身份、角色和本次接入任务，成功后立即使一次性凭据失效。

配对接口只允许受限初始化操作，不拥有 build/deploy 权限。设计中必须包含有效期、错误次数限制、消费的原子性与重放拒绝；在完成 TLS 接入前不传递长期凭据。

长期 token 与仓库密码存入本地凭据文件或机器端受限配置，不写入项目公共配置、初始化日志或 URL 查询串。首版采用本机专用目录与 0600 文件权限；系统钥匙串作为后续可替换后端。

### 4.5 镜像仓库

先支持用户已有的兼容 Registry：填写地址和命名空间，再按用途输入构建机推送凭证、运行机拉取凭证。登录失败时说明在哪台机器、哪一步、哪类权限不足。

连接检查分成三种结果：地址可达、认证成功、推拉权限实测通过。前两项不冒充第三项。完整实测使用明确命名的测试镜像，显示写入范围后执行；首版不自动删除远端 Registry 中的对象，记录测试对象供用户按仓库能力管理。

### 4.6 审阅、保存与首次发布

最终显示摘要：应用、源码方式、构建机、运行机、镜像仓库、业务端口、健康检查、将写入的文件。展示检测依据与待处理项，但不展开内部协议字段。

通过校验后原子写入配置，保存初始化进度并给出 `ship release`。用户选择首次发布时，调用同一发布编排模块，不另建一套构建部署逻辑。

未完成项持久化；再次 `ship init` 从实际检查结果恢复。用户取消只保留必要草稿，不自动销毁已经存在的机器或卸载服务。

## 5. 日常发布与故障处理

### 5.1 来源与目标必须确定

初始化时明确选择 Git 已推送提交或本地目录模式，并持久化这个选择。已有配置保持当前默认行为；新手配置按已确认的来源和目标执行。命令行参数优先于持久化选择。

存在未提交修改但使用 Git 模式时，应显示“本次发布不包含这些本地修改”；不擅自切换成上传本地目录。多个目标时不静默选错环境，显示本次部署对象。

### 5.2 进度与结果示例

以下是目标交互示意，不是现有命令输出：

```text
正在发布 demo-web → staging
源码：已推送提交 a1b2c3d

✓ 检查运行环境
✓ 构建镜像
✓ 推送镜像
✓ 部署应用
✓ 健康检查通过

发布成功
运行版本：a1b2c3d
业务地址：https://app.example.com
查看状态：ship status --to staging
回滚上一版：ship rollback demo-web --to staging
```

业务 URL 来自用户明确配置或经验证的访问映射，不从 agent 管理域名推断。只验证宿主机本地健康接口时，单独标明公网业务访问尚未验证。

### 5.3 失败结果与恢复

| 情况 | 对用户的说明 | 提供的下一步 |
| --- | --- | --- |
| 配置不完整 | 缺少具体项目及影响 | 回到向导对应步骤 |
| agent 连不上 | 区分 DNS、TLS、鉴权、角色与服务不可达 | 给出对应机器和复检命令 |
| 构建失败 | 保留关键错误与完整日志位置 | 修复源码或构建配置后重试 |
| 新版失败、旧版已恢复 | 明确本次发布失败、当前运行旧版 | 查失败原因并验证旧版业务 |
| 新版失败、恢复也失败 | 明确服务状态待处理 | 查看任务/运行机日志并人工恢复 |
| 客户端超时或断连 | 任务可能仍在服务器执行 | 用原 jobId 查询，不重复提交 |

保持现有退出码 0–6 的含义。人类可读提示与 `--json` 输出共享同一结果模型，JSON 模式不夹杂交互文字或 ANSI 控制字符。

### 5.4 回滚与清理

向导式回滚先显示当前版本和上一版本、环境变量是否随快照恢复，再调用现有回滚能力。首版只支持现有的上一发布回滚；任意历史版本选择需要先补齐后端能力，不能只加选择菜单。

GC 保留预览优先：显示候选、保护对象和删除范围；执行后展示 jobId 与分类结果。回滚不恢复数据库，GC 不代表清理整个磁盘或远端仓库。

## 6. 配置、状态与实现分层

以下为设计约束，字段需要在实施阶段加入类型、schema、迁移与测试后才能使用。

| 数据 | 存放与规则 |
| --- | --- |
| 应用规范 | 继续使用 `ship.yaml`，可提交版本管理 |
| 机器和仓库配置 | 继续兼容 `ship.config.yaml`，支持新增凭据引用；不自动改写现有明文凭据 |
| 凭据 | 首版本机专用目录内 0600 文件，agent 端使用受限配置；日志、草稿不含秘密 |
| 默认发布来源/目标 | 增加明确的配置字段；旧配置无字段时保持行为；CLI 参数优先 |
| 初始化进度 | 拟存 `.ship/init-state.json`，含 schema 版本、步骤、脱敏资源标识与检查状态，并加入忽略规则 |
| 配对临时状态 | agent 端保存哈希或等效验证材料、有效期、消费状态；不保存可重放的明文日志 |
| 发布恢复信息 | 记录目标与 jobId，重连查询真实终态；不得把客户端中断当成远端取消 |

新增凭据引用由统一 resolver 解析，例如未来的 `tokenRef`；与明文 `token` 的优先级和互斥规则必须明确。当前字符串不会自动展开环境变量，不在文档里提前提供会失效的占位语法。

实现层建议：CLI 只做输入输出；向导服务维护步骤和状态；项目检测器生成候选；凭据模块管理秘密；安装/配对模块接入机器；现有 pipeline/provider/API 负责实际构建部署。错误分类与恢复指引集中维护，避免每个命令复制一套判断。

复用现有 [pipeline](../src/cli/pipeline.ts)、[doctor](../src/cli/cmd-doctor.ts)、[agent 路由](../src/agent/routes.ts) 和配置校验。`doctor` 保持只读，安装/写入类修复由明确动作触发。

所有新增源码遵循项目结构标准：单文件不超过 200 行、职责单一、依赖无环；不得将整套向导塞入 `main.ts` 或一个大型 `cmd-init.ts`。

## 7. 分阶段任务与验收标准

所有任务初始为“待开始”。每个阶段独立验收；不能因为菜单、截图或模拟测试通过就把整个新手流程标记完成。

### M1：安装即用与配置向导

| ID | 任务 | 验收标准 |
| --- | --- | --- |
| UX01 | 版本化安装产物 | 制作包含 CLI、agent 编译产物及 bootstrap 资源的可安装包；在仓库外全新目录安装后 `ship help` 可用；Node 版本不符有明确指引 |
| UX02 | `ship init` 项目检测 | 对已有 Dockerfile 的单应用给出名称、路径、端口候选；多候选需选择；缺少条件可保存进度 |
| UX03 | 配置预览与生成 | 不手写 YAML 完成现有 agent 的接入配置；通过 schema；重跑不覆盖用户改动；写入失败不损坏旧文件 |
| UX04 | 向导与自动化兼容 | TTY 可交互；非 TTY 缺少输入立即返回结构化缺项，不无限等待；取消和重跑均可恢复 |

首版分发先做版本化 npm tarball 的本地安装验收，确认资源路径和依赖完整；正式发布到 Registry 或下载站另行确定地址与发布权限。不要在使用文档里假定公开的 `shipkit` 包名已归本项目所有。安装器不静默修改用户 Node 版本。

**M1 边界：** 可对已准备好 agent 的环境简化配置，尚不能宣称全新服务器开箱即用。

### M2：首次接入闭环

| ID | 任务 | 验收标准 |
| --- | --- | --- |
| UX05 | 受控安装与升级 | 管理员单条命令安装；版本/产物校验；保留既有凭据；失败可识别并恢复；不覆盖其他站点 |
| UX06 | HTTPS 接入与短期配对 | 真机完成可信入口与配对；过期、重放、错误身份和角色拒绝；日志不含长期秘密 |
| UX07 | 仓库凭证与推拉检查 | 构建机实际推送、运行机实际拉取受控测试镜像；按角色分发凭据；错误权限给出准确原因 |
| UX08 | 初始化状态恢复 | 中途断开后从实际状态继续；不重复安装，不再次消费已用配对凭据；配置和远端状态一致 |

**M2 门槛：** 从干净的专用服务器到首个应用发布全程完成，且已验证 TLS 实机链路。未满足时继续把“首次安装由管理员准备”写明。

### M3：日常操作可理解

| ID | 任务 | 验收标准 |
| --- | --- | --- |
| UX09 | 来源/目标与发布进度 | `ship release` 使用已确认来源与目标；不同阶段有结果；Git 未提交修改不被误报为已发布 |
| UX10 | 错误分级与任务恢复 | 退出码 0/4/5/6 显示对应终态；断连后查询同一 job，不产生重复发布 |
| UX11 | 回滚/GC 引导 | 展示真实可回滚快照和清理候选；明确数据库边界；真实 GC 完成后才报告清理成功 |
| UX12 | 文档与新手实测 | 图文手册缩短为按向导操作；未参与实现的人独立完成首次发布、再次发布与回滚，记录求助点 |

### M4：覆盖更多项目与高级模式

- [ ] 为明确支持的无 Dockerfile 项目提供模板；每个模板完成真实构建、启动、健康检查，不凭框架名保证适配。
- [ ] 完成动态构建机 DNS/反代路由、证书、凭证注入和到期销毁的真实闭环，再纳入向导高级选项。
- [ ] 在实际需求出现后扩展多应用/monorepo 选择、系统钥匙串和更多安装平台。

M4 不阻塞固定机器场景的 M1–M3 交付。

## 8. 哪些现在做，哪些留给平台化

| 当前工具链 | 后续平台 |
| --- | --- |
| CLI 安装、项目检测、配置向导 | 组织账号、团队空间与成员管理 |
| 机器安装/配对、TLS 检查、凭据管理 | 跨团队权限和集中凭据治理 |
| 发布进度、失败解释、任务重连 | 多人审批、发布日历和组织策略 |
| 默认目标、回滚预览、GC 结果 | 集中资源池、配额与成本分摊 |
| 本地可追溯的操作记录 | 集中审计、跨项目报表和告警平台 |

当前工具链需要可靠边界和可核实结果；这些不等待平台化。平台未来复用相同配置、API 和结果模型。

## 9. 验证方式与停止条件

代码层验证覆盖检测器、配置写入、凭据引用、非交互模式、配对过期/重放、断连恢复和结果映射；CLI 集成验证用真实子进程观察 stdout/stderr 与退出码。已有测试保留，新增测试针对行为风险，不只镜像实现。

发布包验收必须离开 monorepo 工作目录，在干净用户目录安装运行，防止漏带 bootstrap 文件、误用源码路径或依赖工作区链接。

真实环境按 [验收清单](audits/2026-09-29/acceptance-next-steps.md) 单独记录：固定机 TLS 是 M2 的前置验收；Docker 长 GC 是对应清理体验的验收；云端到期销毁是动态模式进入新手路径的前置验收。

缺少域名、机器权限、仓库权限或测试资源范围时，继续完成不依赖这些输入的本地任务，将相关场景记录为“等待环境”，不伪造通过。授权范围变化、生产目标不明、预算或删除对象不明确时，停在具体执行前。

验收记录包含版本、环境、输入范围、命令、结果、日志和剩余问题；演示图与模拟测试分开标注。

## 10. 建议的第一个实施切片

**先做 UX01–UX04：安装产物 + 对已有 agent 的 `ship init`。** 这个切片无需创建云实例，可先验证新手是否真的少写配置。

交付内容：

- [ ] 仓库外可安装运行的版本化产物与安装说明。
- [ ] 识别已有 Dockerfile、确认应用信息和现有机器入口的向导。
- [ ] 配置差异预览、原子写入、取消恢复和非交互行为。
- [ ] 本地与 CLI 集成验证记录，以及更新后的使用文档。

明确不包含：生产服务器改动、公开发布安装包、SSH 控制通道、云实例创建/销毁、自动 Registry 开通及通用框架模板。

完成后更新本方案各任务状态，并记录仍需管理员准备的内容。M1 通过后推进 M2，再以真实首次发布验证整条新手路径。
