## E3 仓库限流与状态读取修复

真实页面登记自身 Git 项目后，匿名仓库 API 配额耗尽，提交读取返回 403（remaining=0）。旧路径每次读取状态重新解析仓库，并将限流误判为凭据拒绝；此时页面无法进入计划核对。

限流处理模块 `21dbc81c` 区分主限流 403、有效 `Retry-After` 的二级限流和 429，普通 401/403 保留权限拒绝。API 使用固定提示和最多一天内的 ISO 重试时间，不回传仓库响应正文，也不新增自动重试、重定向或 DNS 绕过。依据 [GitHub 官方限流说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。核心实际 HTTPS/头字段回归 15/15、API 受控响应与实际过滤器测试 3/3；独立复核均无跳过。

登记快照修复采用现有按项目与修订隔离的加密信封，仅状态/历史读取已核对的发布定义。计划和显式检查仍重新读取；私密凭据只投影真实 token/username，公开仓库的加密元数据不被误报为“已配凭据”。源修订、仓库/ref/定义路径、提交和应用身份必须匹配，存在坏快照不能退回未验证的新内容。此记录时修复版尚待真实部署与页面验收，不作为 E1–E3 完成证据。

登记快照模块的新加密与真实 SQLite 回归 8/8、旧仓库 HTTP 回归 1/1，API 类型检查通过。计划/账本针对性回归 4/4，核心私密计划、指纹、执行与清理回归 20/20；本机临时端口首次被沙箱拒绝后，仅开放本机隔离端口重跑通过。夹具中的仓库读取计数用于证明调用路径，不冒充生产网络验收。
