# M2-R2 fd 凭据协议独立复核（2026-09-30）

## 结论

**M2-R2 仍开放（P2）。** 原子 open 返回 fd 可以绑定本次创建的 inode，消除了上一轮“mkdir 后首次采样已换代”的直接根因。但新的清理流程会先移走仍存活的回收者槽位，再检查其身份；这重新暴露了可被第三方取得的空窗。已通过最后一次槽位检查的旧回收者，恢复后仍能覆盖后来持有者的活锁。

本轮独立 build/typecheck 均 exit 0，246/246 Node 回归、17/17 安装器检查和生成物漂移检查通过。未重跑安装包冒烟。R1、R3 和结构整顿维持此前范围。本轮没有修改业务源码。

## 失败位置与确定性交错

- `src/shared/file-lock.ts:96`：inspectPrev 无条件 rename(prev, aside)，发生在读取 PID、判断存活之前。
- 161–167 行：候选者通过两次槽位检查后，仍存在检查与 rename(claim, lock) 之间的窗口。
- 168–169 行：替换后的 token 自检只反映读取时刻，不能撤销早先已进入的其他临界区。

复现步骤：

1. 原锁持有者已死亡。A 原子创建 prev，写入活 PID，通过两次槽位检查及死锁身份检查，在替换主锁前暂停。
2. B 尝试回收，实际执行 rename(prev, aside)，把 A 的活槽位移走，在移走后暂停。
3. C 发现原 prev 路径空闲，创建自己的槽位并通过检查，替换主锁，自检成功，进入并保持临界区。
4. A 恢复执行此前已获准的 rename，覆盖 C 活锁，自检也成功，进入临界区。
5. 实测 `maxActive=2`、`activeAtObservation=2`、`overwroteLiveC=true`、`cLockChanged=true`；`prevMissingWhileALive=true`。A 槽位记录 PID 与当前活进程 PID 一致。

此场景不需要等待 500ms，也不需要任何回收者崩溃。所有 fs 操作真实执行；只在 A 替换前、B 移走后暂停调度。

## 为什么 fd 与最后写者检查不足以保证互斥

fd 保留创建对象的身份，但不阻止其他调用把路径移走。最后一次 stat 通过之后，候选者仍可能失去路径上的槽位；之后再无条件替换主锁即会踩到新的持有者。

“并发替换收敛到最后写者唯一”只描述最终文件内容，不能保证临界区唯一。C 完成替换并自检后可以保持执行，A 随后替换并自检也可成功，二者自然重叠。事后恢复 aside 或再读一次 token 都不能撤销已经发生的并发。

现有两方测试没有覆盖“旧候选者通过最后检查、清理者移走并暂停、第三方完成进入、旧候选者再恢复”的三方时序。

## 下一轮要求

1. 修复从回收资格确认直到进入并持有临界区期间的持续排他性。不能仅增加检查次数或依靠最后写者自检。
2. 不得先移走可能仍存活的回收者来制造新的可领取槽位；也不能简单改成先判活再 rename，而忽略身份检查与路径变更的竞争。
3. 清理、资格撤销、恢复、最终替换必须作为完整协议处理，保留崩溃恢复与统一超时。若改用成熟原语，验证平台、进程内/跨进程及离线分发语义。
4. 将上述三方时序转为持久回归。C 进入并保持时 A 不得进入或覆盖；C 释放后等待者最终能够获得。允许新协议更早阻断路径，但不能删除互斥与最终进展断言。
