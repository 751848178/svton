# M2-R2 `.prev` 协议独立复核（2026-09-30）

## 结论

**M2-R2 仍开放（P2），本轮协议不能关闭竞争接管问题。** 发现范围仍为原 M2-R2：回收者会覆盖仍存活的新持有者，使共享状态事务失去互斥。M2-R1、M2-R3 与安装脚本结构整顿维持此前通过结论；本轮没有扩大功能范围。

## 唯一阻塞：按旧锁 mtime 清理 `.prev`，破坏回收者互斥

位置：`src/shared/file-lock.ts:103–121`，尤其 109–110 行的年龄清理和 121 行的无条件替换；阈值在 42 行。

`link(lock, prev)` 创建的硬链接与原锁共享 inode，mtime 也是原锁的修改时间。它既不记录回收者身份，也不记录回收开始时间。当前实现仅凭 mtime 超过 500ms 就允许竞争者删除 `.prev`，无法证明原回收者已经退出。源码同时将 `.prev` 描述为“非互斥载体”和“唯一串行化点”，而实际排他性依赖它不被竞争者删除。

确定性交错：

1. 原持有者已死亡；A 创建 `.prev`，通过身份校验，在 `rename(claim, lock)` 前暂停。
2. B 发现 `.prev` 的 mtime 超过 500ms，删除它，重新取得旧锁证据。
3. B 替换旧锁并进入临界区，继续持锁。
4. A 恢复，无条件用自己的 claim 覆盖 B 的活锁，自检得到自己的 token，也进入临界区。
5. 实测 `maxActive=2`、`activeAtObservation=2`、`aOverwroteLiveB=true`。

这意味着共享凭据/配对状态的读改写事务仍可能相互覆盖；本轮直接证明的是双重进入和活锁被覆盖，没有伪称已观察到生产凭据丢失。

## 两个独立复现场景

| 场景 | 调度与文件条件 | 结果 |
| --- | --- | --- |
| 活回收者暂停 | A 持 `.prev`，在替换前暂停 650ms；随后 B 接管 | 最大临界区并发 2，A 覆盖 B 活锁 |
| 旧锁继承时间 | 先让死锁文件自然老化 650ms，再让 A 取得 `.prev`；A 持证后不额外设置年龄等待，启动 B | 同样最大并发 2；新 `.prev` 立即满足“过期”条件 |

两个脚本都使用真实文件系统与真实退出子进程的 PID，并先确认 ESRCH。仅在 `rename` 前插入调度暂停，不伪造文件操作结果或 PID 存活结果。A/B 是同一进程中的并发调用，使用 AsyncLocalStorage 区分调度；这是协议级确定性交错验证，不冒称独立进程端到端测试。包内正常配对并发另由真实 agent 与管理员子进程验证通过。

实测 `.prev` 与原锁 inode 相同、mtime 相同。第二个场景说明本缺陷不要求新回收过程本身耗时超过 500ms。

现有 `file-lock-race.test.ts` 的 v1 在持证窗口只等待 250ms，对新鲜锁没有跨过 500ms 清理阈值，也没有覆盖旧锁 mtime。当前 236 项全绿因此不能排除这个窗口。

## 下一轮仅修 M2-R2

- 明确回收权的身份与生命周期。慢、暂停中的活回收者不能因时间阈值丢失回收权；退出的回收者仍需可恢复。
- 替换前的排他保证必须覆盖“清理证据—另一个回收者接管—原回收者恢复”的完整交错。单次原子 rename 或额外一次 read/check 都不自动建立这个保证。
- 不接受仅增加 500ms 阈值、缩短测试暂停、无条件禁用残留恢复等修补。可评估适用平台的操作系统锁或具有明确所有权与崩溃恢复规则的协议，并说明打包/安装兼容性。
- 将上述两种失败转为持久回归，保留临界区实时并发计数、B 活锁不被改写、退出码和磁盘状态断言；覆盖回收者在各阶段崩溃后可恢复。保留已有活持有者、旧释放者、多竞争者、不可读锁、真实子进程与包内配对测试。
- 只在这些场景修复且原有回归通过后关闭 M2-R2；无需重开 R1/R3 或扩展 M3/M4。
