## 唯一剩余项：M2-R2 · P2 · 回收旧锁时可能移走新持有者的锁

位置：[file-lock.ts](../../../src/shared/file-lock.ts) 的 reapIfDead（第 73–91 行）。

PID 存活判断解决了旧的“按锁龄直接抢占”问题，但“两次读 token → rename → 移动后再核对 → 不一致时 link 回填”仍不是条件原子操作。第二次读和 rename 之间，锁可能已由其他事务接管；rename 会把新持有者的锁移走。此时锁路径短暂不存在，另一个调用可通过 wx 创建新锁并进入。事后发现移错、尝试回填时，路径已被占用，link 的 EEXIST 又被吞掉，无法撤销已经发生的双重进入。

### 确定性复现

使用未修改的编译后锁模块、真实文件系统和一个真实已退出子进程的 PID 作为残留锁持有者。通过 node:test 的模块替身**只控制 rename 前后的暂停时序**，不伪造文件内容、系统调用结果或错误。三个调用在同一测试进程中模拟可发生的异步/进程调度交错，不将此称为三进程端到端测试。

1. A 读到死持有者的旧锁，两次 token 检查都完成，暂停在 rename 前。
2. B 正常回收旧锁，获得新锁并进入临界区，保持运行。
3. A 恢复，rename 移走的实际是 B 的新锁；暂停在移动后的身份核对之前。
4. C 看到原锁路径空缺，wx 成功，进入临界区；此时 B 仍在运行。
5. A 核对发现 token 不符，link 回填因为 C 的锁已经存在而失败；A 最后超时，但 B/C 的重叠已经发生。

独立结果：`bAndCOverlap=true`，采样时 `bActive=true, cActive=true`，留下 1 个 `.reap-*` 文件。A 超时或没有进入自己的临界区，不能证明 B/C 的互斥仍成立。

脚本：`/tmp/codex-tool-runs/svton/m2-final-20260930/lock-reap-check.mjs`。运行命令：

```sh
node --experimental-test-module-mocks /tmp/codex-tool-runs/svton/m2-final-20260930/lock-reap-check.mjs
```

脚本原文与结果也已持久保存到 [本次证据 JSON](m2-closure-recheck-evidence.json)，不依赖临时目录长期存在。

### 修复验收条件

- 重设计接管协议或使用有正确互斥保证的锁原语，确保检查、移走和接管之间不能让活跃持有者的锁路径出现可被第三方获取的空窗。
- 不能仅再增加一次 token 检查、延长超时或忽略回填失败；这些都不能撤销第三方已经进入临界区的事实。
- 将上述 A/B/C 调度转为持久回归，同时保留活跃持有者不被抢占、真实崩溃残留回收、旧持有者延迟释放与普通并发回归。
- 关键断言是整个过程中临界区最大并发数为 1、成功返回的凭据可认证且状态无丢失更新；不能只断言回收者最后返回超时。
