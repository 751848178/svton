## 待修复问题

### R1 · P1：切换已有目标会把 staging 连接信息写入 prod

位置：[machines.ts](../../../src/cli/init/machines.ts) 73–83 行；[wizard.ts](../../../src/cli/init/wizard.ts) 114–118 行。属于机器/目标绑定与多目标保留的修复回归。

`machineDefaults` 在提问前选好默认目标的 URL/token。用户随后将 `targetName` 改为已有的 `prod` 时，`askMachines` 没有重新读取 prod 对应配置，而是继续使用此前 staging 的 URL/token 默认值。确认保存后，prod 项被改成 staging 机器。

独立复现：配置同时含 staging=A、prod=B，仅将目标名称选择为 prod，其余回车保留；向导返回 ready=true，保存后 `runtime.targets.prod.url` 变成 A。新 token 不再跨 URL 发送的原始问题虽已修复，但 target 名与连接信息仍未正确绑定。

修复要求：选定 targetName 后再从该目标解析 URL/token 整组默认值；新建或重命名目标明确区别于选择已有目标。覆盖从 staging 切换 prod、反向切换、新目标与显式替换机器。

### R2 · P1：忽略规则被后续否定时，秘密配置仍会进入 Git

位置：[gitignore.ts](../../../src/cli/init/gitignore.ts) 48–52 行。对应 M1-03 的遗漏。

规划器先判断文本中是否存在同名行，存在就跳过；即使 `git check-ignore` 已判定该文件实际未被忽略，也不会修正或警示。例如：

```gitignore
.ship/
ship.config.yaml
!ship.config.yaml
```

独立复现：在上述规则下执行真实 `ship init --json`，exit 0、warnings 为空，`git check-ignore -q ship.config.yaml` 仍返回 1。保护秘密文件的承诺没有覆盖规则优先级。

修复要求：以 Git 的有效判定为准，不以“某行出现过”为准；在审阅中明确展示需调整的冲突规则，或拒绝宣布保护完成并要求用户处理。写入后复检实际忽略结果，并覆盖否定规则、子目录和已有跟踪状态。

### R3 · P2：没有内容差异时，凭据文件仍保持 0644

位置：[write.ts](../../../src/cli/init/write.ts) 78 行；[wizard.ts](../../../src/cli/init/wizard.ts) 159–162 行。对应 M1-08 的遗漏。

变更判断只比较文件文本，未检查秘密文件现有权限。安全写入函数只在改写时执行，因此对内容已经规范化的 0644 配置，init 直接走“无需写入”成功分支。

独立复现：先完成 init，将配置权限改为 0644，再执行真实 `ship init --json`；exit 0、`wrote: []`，权限仍是 0644。

修复要求：将权限要求纳入计划和幂等检查；即使文本不变，也应修正权限或明确返回待处理状态。验证“内容相同但权限不符”和安全写入失败两条路径。

### R4 · P2：恢复和清空选择仍不能可靠保留

位置：[wizard.ts](../../../src/cli/init/wizard.ts) 97–108 行、取消分支；[questions.ts](../../../src/cli/init/questions.ts) 64–66 行；[plan.ts](../../../src/cli/init/plan.ts) 端口序列化/合并。对应 M1-07 与 M1-11 的不完整收口。

独立复现三个正常操作分支：

1. 已有端口 `8080:3000`，向导改为 `9090:3000`，在机器步骤取消。草稿保存了新值，但恢复时现有文件无条件优先，默认又变回 `8080:3000`；文件指纹未变化，草稿仍有效。
2. 上次已保存应用答案，恢复时在第一个问题再次取消；catch 将新建的空 progress 写回，原 app 字段消失。
3. 用户通过清空操作删除端口映射，保存时空数组被删除为“没有 ports 字段”；再次 init 将其当作未配置，根据 EXPOSE 恢复 `3000:3000`。清空操作能输入，但意图未被持久化。

修复要求：通过指纹验证的未完成草稿优先于未变化的旧配置；取消前合并保留尚未重新作答的字段；用明确的空值/空列表表达“用户主动禁用”，不等同于未知值。完成“修改→取消→恢复”“恢复→再取消”“清空→保存→幂等重跑”的行为验证。

### R5 · P2：新增文件已删除，回滚校验仍误报部分失败

位置：[apply.ts](../../../src/cli/init/apply.ts) 49–55、65–69 行。对应 M1-06 的遗漏。

当原文件不存在，回滚正确删除本轮新建文件；但 `verifyRestored` 仍尝试读取它，ENOENT 被当作恢复失败，导致“回滚仅部分成功”的错误结论。

独立复现：新建项目，令配置路径为目录以触发写入失败；先创建的 ship.yaml 已正确删除，错误结果却是 `rollback: partial`，把 ship.yaml 列为未恢复文件。

修复要求：`before === null` 时以目标不存在为恢复成功；原文件存在时再校验原内容与原权限。报告要反映实际恢复状态，避免让用户对不存在的问题执行手工恢复。
