## 2. 先完成的代码与本地验证

### A. 修复定时器契约

- 按真实 SDK 的 `ActionTimers` 字段修正读取、类型与测试数据；优先复用官方类型或建立受其约束的适配器，避免另写一个可随意漂移的响应结构。
- 模拟响应应通过官方类型约束，例如使用 `satisfies`；不能仅把实现和测试中的字符串同时替换便认定全部完成。
- 增加符合 SDK 形状的成功样例，以及缺失/空数组、其他实例、错误动作、错误期限、不可解析时间和错误执行状态的拒绝样例。只有与目标实例及预定销毁期限相符、状态适合准入的定时任务才可通过。
- 在 provider 集成测试中证明：正确响应不会误触发补偿；查询失败或不匹配不进入 ready；实例账本先落盘，补偿结果有明确记录。
- 运行 build、typecheck、完整测试。代码验证完成后，才进入账号可用性和云端实际执行验收。

### B. 先做隔离长 GC 验证

长任务协议不依赖生产机器有大量镜像。先通过本机临时工作目录、模拟/可注入 Docker runner 和本地 HTTP agent 验证：

- GC 持续超过原 20 秒请求窗口时，提交请求仍及时返回 jobId，客户端能够继续轮询至终态。
- 断开提交客户端后，服务端结果仍可通过 jobId 查询，日志和最终结果可追踪；这里不把客户端断开混同于 agent 重启。
- GC 与部署/回滚交错时锁确实生效，保留版本受保护；Docker 失败能返回可判别错误。
- 大量账本条目和长执行时间分别构造，不能用“数据多”替代“执行跨过超时窗口”。

之后在专用 Docker 测试环境验证真实删除：只创建可识别的测试镜像和容器，先预览候选，再删除允许范围内的测试对象；验证当前版本和上一版本仍能离线恢复。禁止用生产机器的全局 prune 作为验证手段。

### C. 核对 TLS 的可部署性

固定机 Caddy 模板、动态 agent endpoint 和 bundle 分发必须共同构成实际可达链路。当前动态 URL 仍以 IP 拼接，不能只把 scheme 改成 https 就认为证书身份、反代和隧道已接通。

先在本地检查配置和 URL 生成能力：连接地址是否能表达选定域名/入口，是否与证书身份一致，bundle 的外部 URL 是否映射到真实分发路径。如果缺少必要的 endpoint 配置或安装接入，应先补代码/模板；已有满足需求的配置能力则不重复建设。不得关闭证书校验或编造域名、证书与隧道。

以上 A/B/C 的本地部分不需要生产部署权限，也不应因缺云环境而停止。
