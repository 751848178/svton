# Shipkit 脚本状态文件锁本轮收口复核（2026-10-04）

**本轮保留 1 项确定发现：REG-03 的故障恢复遗漏 choosing 标记。** 上轮目录枚举错误放行、回调退出时清理错误卡住 gate、重试 bind 超预算、正常过期 temp 残留均已在原场景复核通过；WAIT-01 的上轮问题通过复核。当前仍使用端口注册表和面包店发布队列，本轮按实现行为验收，未将是否采用简化建议列为通过条件。

范围仅为本机脚本状态文件锁。没有修改运行时代码。本次发现影响故障解除后的继续运行，未在本次测试中观察到双重进入或丢更新。源码哈希、复现脚本、结果和日志见[证据 JSON](m2-r2-script-lock-closure-evidence.json)。

## [P2] choosing 标记清理失败未进入恢复记录

位置：[`lock-pubmutex.ts:172`](../../../src/shared/lock-pubmutex.ts#L172) 删除 `.pubc-*`；外层 finally 只对 `queueDir` 清理失败登记 `leakedSlots`（183–192 行）。因此回调开始前删除 choosing 标记失败时，虽然进程内 gate 已能结算，choosing 标记却仍在盘上且不属于下一轮恢复集合。进程仍存活，后继获取把它作为活 choosing 者一直等待。

真实私有目录复现：

1. 完成 queue 目录创建后，临时撤销父目录写权限，使 choosing 删除实际返回 EACCES；首次回调没有执行。
2. 恢复目录权限。磁盘上仍有本次 `.pubc-*` 和 `.pubq-*`。
3. 同进程、同 key 再次获取，250ms 预算约 **256ms** 后失败，回调没有执行。queue 已恢复清理，但 choosing 仍残留。
4. 仅删除本轮确切的孤儿 choosing 标记，立即可重新进入，证明故障已经解除而恢复记录漏项。

复现仅在 mkdtemp 私有目录使用真实 mkdir/chmod/rm；包装 mkdir 只在真实 queue 创建后施加权限故障，不伪造系统调用结果，不修改公共注册表。原语的调用链来自 `claimPort → withPublishMutex`；此故障发生在首次发布之前，未创建 claim。进程退出后他人可按死亡 PID 回收，但存活进程内重试无法自行恢复，不满足既定“故障解除后可重新获取”的要求。

现有 [`file-lock-faults.test.ts`](../../../src/shared/file-lock-faults.test.ts) 的清理失败测试在业务回调内部撤销写权限，覆盖 queue 清理，遗漏 choosing 阶段。

## 最小修改建议

在现有方案中统一跟踪本次**成功创建**的 choosing 和 queue 标记。两个阶段的清理失败都按准确名称登记到自身残留恢复机制；进程内 gate 无论哪个阶段失败都要结算；恢复时只清理已结束调用留下的准确名称，不能删除另一活调用的标记。

增加本轮时序为持久回归，断言首次回调不执行、恢复权限后同进程同 key 无需人工清理即可获取、两类标记都被清空，并保留现有回调退出时清理失败的回归。本轮无需为了这一发现重新设计发布协议，也不能靠延长等待时间消除该阻塞。

## 可直接使用的修复提示词

只修本机脚本状态文件锁的 choosing 清理恢复遗漏。先读本报告及 evidence JSON。当前 `lock-pubmutex.ts:172` 的 `.pubc-*` 删除失败不会登记到 `leakedSlots`，外层只记录 queueDir；因此故障解除后，同进程仍被自身活 choosing 标记阻塞。最小修复是记录本次成功创建的 choosing/queue 两类标记，对两者统一执行准确名称清理与失败恢复，并保证任一清理阶段失败时 gate 都结算。添加“queue mkdir 成功后撤销目录写权限 → choosing 删除 EACCES → 恢复权限 → 同进程同 key 再次获取”的持久回归：首次回调不执行，第二次无需人工删标记即可成功，pubc/pubq 均清空。保留本轮已通过的枚举故障、queue 清理、deadline/temp、晚 rename、同键串行和故障恢复回归。运行 build/typecheck、锁回归、全量、打包/包冒烟并留档；独立复核前只将此恢复项保持开放，不重开已通过问题或扩大其他场景。
