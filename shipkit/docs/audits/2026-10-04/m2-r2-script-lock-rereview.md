# Shipkit 脚本状态文件锁复核（2026-10-04）

**结论：REG-03 / WAIT-01 尚不能关闭。** 上轮 owner 目录抢占已被替换，旧发布竞争重放得到同时持有数 1、终值 2；原 250ms 分配暂停下的 50ms 获取预算现在约 50.16ms 返回，业务回调不执行。但目录枚举故障仍会放行两个发布者，清理失败会卡死进程内队列，后续 bind 和过期临时文件清理也有缺口。

本轮范围仅为本机脚本状态文件的安全互斥、超时和故障恢复。未修改运行时代码。测试使用合成状态文件、自建子进程与监听；权限故障仅施加在专属临时目录。完整记录、源码哈希、复现源代码和命令见[证据 JSON](m2-r2-script-lock-rereview-evidence.json)。

## 1. REG-03：目录读取失败被当作空队列，破坏互斥（P2）

位置：`src/shared/lock-pubmutex.ts:76`（`scanQueue`）、`:128`（取序号），以及 `src/shared/lock-registry.ts:112` 的目录枚举。三个位置都使用 `readdir(...).catch(() => [])`。

目录不可枚举时无法判断其他发布者是否存在，当前代码却把这个未知状态作为“无人排队”。在暂时保留目录写入与路径遍历权限、撤掉枚举权限的真实文件系统故障下，B 的已提交发布槽位被 A 忽略。

完整 `withFileLock` 双子进程复现：先临时占用首选候选，让 B 选择端口 61046 并暂停在发布 rename 前；释放临时监听，令专属测试注册表的 `readdir` 实际报 EACCES；A 忽略 B 的槽位，发布 61134 并进入；恢复目录权限后 B 完成原 rename，改写为 61046 并进入。A/B 均读到 0，重叠为 true，最终计数 **1（应为 2）**。

为避免修改公共注册表，复现通过模块包装将固定注册表路径映射到本轮新建 `/tmp/.../registry`；路径以外的真实 fs 调用及返回结果未替换。另一个直接调用 `withPublishMutex`、完全无模块 mock 的权限故障试验也得到双重进入和终值 1。根因是故障后继续授权，不需要其他使用场景。

修复要求：读取队列或已占用端口集合失败必须显式保守失败或在同一 deadline 内重试，不能转换为空集合继续发布；测试需断言故障期间不进入业务回调、不改写活映射，恢复权限后可继续合法获取。

## 2. REG-03：清理失败跳过 release，故障解除后仍不能推进（P2）

位置：`src/shared/lock-pubmutex.ts:147–149`。`finally` 先等待 `rmMarker(queueDir)`，之后才执行 `release()` 和删除进程内链。若删除报错，后两步都被跳过；后续调用永久停在 `:107` 的 `await prev`。

真实临时目录复现：持有 `withPublishMutex` 时将父目录暂时改为不可写，使退出清理报 EACCES；随后恢复权限，再调用同一 key 的发布互斥，设置 100ms 过期条件。350ms 后仍 pending，回调未执行。该复现直接覆盖发布互斥原语；外层 `withFileLock` 的超时竞速可以让调用者返回超时，但无法释放已经被卡住的进程内链。

修复要求：进程内排队权必须在清理成功或失败时都结算，并提供对本次失败清理资源的恢复路径。单独加一个嵌套 finally 释放内存 gate 还不够：遗留的本进程存活槽位也不能永久阻塞后继；恢复过程不得误删其他活调用的槽位。

## 3. WAIT-01：只约束首次分配和 bind，重试 bind 仍可超预算（P2）

位置：`src/shared/file-lock.ts:191–192`。初次 acquiring 与 deadline 竞速，但争用循环的退避和 `bindTracked` 仍直接 await。

复现中先用自建监听真实持有已登记端口，第一次 bind 实际失败，probe 读到本 key 的真实横幅；仅在第二次真实 listen 调用前添加 300ms 可恢复异步暂停。`timeoutMs=150`，结果 **324.29ms** 才返回超时；fn 未执行、token 无残留。暂停只控制调用时机，端口和系统调用成败未伪造。

修复要求：同一获取 deadline 覆盖后续重试和退避；任何晚成功监听均安全关闭。测试需分别覆盖首次分配和竞争后的重试阶段，不能仅以首次 acquiring 的回归代表整个获取流程。

## 4. WAIT-01：过期返回留下临时 claim（P2）

位置：`src/shared/lock-registry.ts:44–51` 的 `publishAtomic`。写入临时文件后若 `expired()` 为 true，就直接 return；只有 catch 分支清理临时文件，正常的过期返回未清理。

将真实 temp 写入完成后的异步恢复推迟 300ms，`timeoutMs=100`：调用约 101.75ms 返回超时，fn 未执行；再等待 650ms，发布队列槽位已清理，但本 key 的 `.json.<random>.tmp` 仍留在注册表中。随后合法获取可以成功，残留仍存在，需由复现脚本清理。

修复要求：成功、异常、过期退出都拥有明确的本次临时文件清理责任，持久回归应等待后台步骤结束后再检查本 key 的残留。

另记录一项边界：在 rename 实际调用前暂停 300ms，100ms 超时约 100.10ms 已返回，但约 344.81ms 后映射仍被发布。该试验未发生业务回调或双重进入；它说明“rename 前检查一次时间”不能保证异步提交绝不晚到。实现方应明确并证明晚完成的安全收尾语义，避免仅用注释宣称不会迟到发布，也不能在补偿时删除后来者正在使用的有效映射。

## 给实施方的提示词

只修 Shipkit 本机脚本状态文件安全锁，保留其他工作树改动。先读本报告和 evidence JSON，重放保存的脚本。修复 `lock-pubmutex.ts` 的枚举失败放行与清理异常卡死进程内队列：不能将 readdir 错误当空队列；cleanup 失败也要结算进程内排队权，且在故障解除后安全恢复自身遗留槽位。修复 `file-lock.ts` 仅对首次 acquiring 竞速的问题，让竞争后的退避和每次 bind 同样受获取 deadline 约束，并关闭晚成功监听。修复 `lock-registry.ts` 中 expired 返回遗漏 temp 清理，明确并验证异步 rename 晚完成后的安全收尾语义。保持超时不执行 fn、活映射不被改写、同键临界区 maxActive=1、两次加一终值=2，以及故障解除后能重新获取。加入以上真实权限故障、清理失败恢复、重试 bind 暂停、temp 写完后过期的持久回归；再跑 build/typecheck、锁回归、全量测试、打包和包冒烟。日志和观察结果留档，实施方验证与独立复核分别标注，未复核前 REG-03/WAIT-01 保持开放。
