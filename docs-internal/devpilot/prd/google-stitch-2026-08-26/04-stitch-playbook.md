# Google Stitch 执行手册

## 1. 目标与边界

本手册用于把 Devpilot PRD 稳定地转成一套可评审、可回溯、可实现的 Stitch 设计稿。Stitch 负责设计探索、屏幕生成和原型串联；仓库代码、API 与本目录 PRD 仍是功能真相来源。

Google 当前公开说明显示，Stitch 支持从自然语言、设计文件和已有代码上下文生成 UI，使用无限画布组织方案，创建交互原型，并通过 `DESIGN.md` 导入/导出设计系统规则；近期还提供实时设计/引导及向 Google AI Studio、Antigravity 等工具的衔接能力。使用时以当前 Stitch 界面实际可用入口为准，不把实验功能当作 Devpilot 的产品能力。参考：[Stitch AI UI Design](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-ai-ui-design/)、[DESIGN.md in Stitch](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-design-md/)、[Stitch updates](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-updates/)。

## 2. Stitch 项目初始化

1. 新建 `Web` 项目，命名为 `Devpilot Console Redesign 2026-08`。
2. 将本目录 [`DESIGN.md`](./DESIGN.md) 作为设计系统导入；若界面仅支持粘贴上下文，则把 YAML 令牌与正文完整粘贴到项目规则。
3. 上传主视觉参考：`project-skills/devpilot-project-workbench-design/assets/approved-project-config.png`。
4. 按批次上传最接近目标状态的 V2 参考图：`evaluation/design/project-module-v2/exports/V2-01...V2-10`。
5. 把 [`03-screen-catalog.md`](./03-screen-catalog.md) 作为 Frame 命名和状态清单；不要让 Stitch 自行改名或合并关键状态。
6. 每次只生成一个批次，验收后再复用已通过的 Shell 与组件。不要在同一提示词里一次性生成整个后台。

## 3. 全局系统提示词

在所有批次前先提供以下约束；后续局部提示词只描述本批新增页面：

```text
你正在重新设计 Devpilot，一套面向研发、运维、审批人与管理员的企业级项目交付后台。

严格遵循已导入的 DESIGN.md、主视觉参考和屏幕目录。沿用获批参考中的 64px 顶栏、236px 左侧导航、紧凑表格、蓝色主动作、浅灰边界和清晰的状态语义。不要创造新的品牌、配色、字体、圆角体系或卡片语言。

核心产品模型：Project 是稳定身份；ReleaseOrder 是用户创建的发布意图；Manifest 是构建产物；DeploymentRun 是一次部署或恢复执行；EnvironmentVersion 是环境当前版本；Gate、Approval、AuditEvent 提供放行与证据。

每个页面必须同时回答：正在操作什么对象、当前有什么问题、问题造成什么影响、用户下一步应去哪里。一个视图只有一个主动作。表单校验贴近字段；阻塞修复动作贴近问题；技术证据放在表格、抽屉或日志视图中。

仅设计屏幕目录中标记为 LIVE、API、DESIGN 或 BACKEND 的能力。DEFER 能力不得画成已经可执行。不得用假流量图、假实时监控、假自动回滚或无数据来源的 KPI 装饰页面。

为每个状态创建独立 Frame，使用真实且跨屏一致的中文示例数据。桌面画布为 1440×1024；指定的移动 Frame 为 390×844。所有状态同时使用颜色、图标和文字表达，满足键盘操作、焦点可见、4.5:1 文本对比和 44×44px 移动触控目标。
```

## 4. 批次 A：后台 Shell 与项目目录

目标 Frame：`SHELL-03` 至 `SHELL-07`、`PROJ-01` 至 `PROJ-03`。

```text
基于全局系统提示词生成后台框架与项目目录。

顶部栏包含 Devpilot 品牌、团队切换、语言、用户菜单；左侧导航按工作台、项目、基础设施、资源、运维、治理、配置、团队、管理、帮助分组。当前页面是“项目”。内容区顶部使用面包屑和页面标题。

项目目录使用紧凑表格，字段为项目、状态、组件、线上版本、最近发布、操作；非生产环境版本列可由用户选择后出现。主动作只有“新建项目”。分别输出默认、筛选无结果、全局错误/无权限和移动导航状态。不要把每个项目做成大卡片，不要用 Dashboard KPI 替代项目列表。

参考 V2-01，保持获批视觉密度和表格层级。Frame 名必须与屏幕目录一致。
```

验收重点：导航完整但不抢占页面注意力；项目、版本和状态是首要信息；空态动作与产生空态的条件一致。

## 5. 批次 B：项目接入、总览与项目信息

目标 Frame：`PROJ-04` 至 `PROJ-09`、`WORK-01` 至 `INFO-02`。

```text
复用已通过的 Shell。设计三步项目接入流程与项目工作台。

第 1 步连接仓库：公共/私有仓库、托管/临时凭据、HTTPS Token/SSH Key、名称、分支、描述和字段校验。第 2 步仓库分析：分别输出运行、失败、待确认；显示默认分支、选定分支、精确提交、凭据引用、项目类型、架构、组件、依赖、端口与证据。第 3 步设置测试/生产环境基线并确认组件。

项目总览显示项目身份、环境版本、组件、最近发布、检查点和一个明确下一动作。阻塞态把问题、影响和修复入口放在一起。项目信息页展示仓库、默认分支、只读发布策略、组件和仓库分析详情。

参考 V2-04。流程页保留步骤位置和已输入内容；失败不清空用户输入；秘密字段永不明文回显。
```

验收重点：分析证据可核查；接受分析是显式动作；项目总览没有混入完整配置表单。

## 6. 批次 C：发布单列表与发布前检查

目标 Frame：`REL-01` 至 `REL-05`。

```text
复用已通过的项目 Shell。设计发布单列表、创建发布单和发布前检查。

发布单列表字段为发布单、状态、源提交、当前阶段、更新时间和操作，支持搜索与状态筛选，主动作“创建发布单”。创建表单包含名称、语义版本 x.y.z、说明和提交来源，使用内联校验。

发布前检查将 Gate 按 commit、build、deploy、promote 分组。分别生成全部 ready 与 blocked 页面。blocked 页面必须把失败 Gate、影响、证据、目标页面深链和刷新时间放在一起，唯一主动作是修复首要阻塞；不可同时出现“立即部署”。再生成一个 Gate 状态目录，解释 checked、unchecked、blocked、warning、manual、unavailable。

参考 V2-03、V2-05。不要把阻塞内容做成巨大营销式卡片。
```

验收重点：阻塞时无法越过 Gate；状态与后端语义对应；列表打开详情、构建或部署记录的路径明确。

## 7. 批次 D：构建与测试部署

目标 Frame：`REL-06` 至 `REL-11`。

```text
设计同一个发布单中的构建和测试部署状态。构建输出运行中、失败、成功；测试部署输出运行中、失败、成功。

构建运行中显示当前轮次、步骤、耗时、日志摘要、取消与历史轮次；成功后呈现 Manifest、制品、源提交和证据。测试部署明确目标环境、使用的 Manifest、阶段、日志、历史运行和验证结果。失败页面将失败步骤、影响和可重试范围放在一起，并保留历史证据。

参考 V2-06。任何进行中进度都要有文字状态，不只显示动画；日志入口是次动作；取消与重试必须说明操作对象。
```

验收重点：多轮构建可区分；测试和生产承诺使用同一 Manifest；失败后不会暗示已经更新环境版本。

## 8. 批次 E：生产、审批、证据与恢复

目标 Frame：`REL-12` 至 `REL-18`。

```text
设计生产发布复核、等待审批、生产运行、成功、失败、证据抽屉和撤回确认。

生产复核必须显示测试版本、生产目标、差异、风险、inputHash 和审批策略；提交审批后内容冻结。等待审批显示审批人、时间、输入哈希和审批记录。生产执行再次强调与测试相同的 Manifest。成功页显示线上 EnvironmentVersion、证据和完成时间；失败页保留当前线上版本，并通过“创建恢复运行”而不是改写历史来恢复。

证据抽屉汇总构建、部署、审批、配置快照、审计记录和可复制 ID。撤回确认说明当前阶段、可撤回范围与后果。

参考 V2-07、V2-08、V2-09、V2-10。不要把审批按钮交给没有权限的角色；不要把“回滚”画成直接修改旧版本。
```

验收重点：审批绑定 `inputHash`；成功、失败、恢复是不同事件；证据跨对象关联一致。

## 9. 批次 F：项目配置

目标 Frame：`CFG-01` 至 `CFG-13`。

```text
设计项目配置的六个环境页签：环境版本、部署目标、资源配置、变量与密钥、访问控制、验证规则。环境选择只列出项目已有环境，默认生产。

环境版本输出列表、详情抽屉、版本切换、升级和恢复预览。部署目标输出列表与新增/编辑，明确 missing、duplicated、provider_mismatch、ssh_root_invalid、ssh_connection_invalid 等就绪问题。资源、变量、访问、验证以紧凑表格或分组表单呈现。再输出不可变配置修订历史和复制/同步预览。

参考 V2-02 和 approved-project-config.png。配置是环境级不可变修订，不要混成一个长表单；秘密只显示遮罩和来源；保存前显示差异与影响。
```

验收重点：环境上下文始终可见；版本动作有预览；目标问题可直接定位修复；修订可追溯。

## 10. 批次 G：域名、入口与部署记录

目标 Frame：`DOM-01` 至 `DOM-05`、`DEP-01` 至 `DEP-05`。

```text
设计项目级“域名与入口”和“部署记录”。

域名页支持环境选择，表格字段为域名、环境、目标、TLS、状态、操作；新增/编辑时项目和环境不可被悄然切换。生产域名缺失要作为发布阻塞呈现，并提供添加入口。配置预览展示站点配置、上游、TLS 与风险；诊断显示探测和同步证据。

部署记录表格显示环境、版本、Manifest、状态、开始/完成时间和运行类型。详情抽屉包含阶段、步骤、日志、目标、审批、配置快照和审计 ID。失败、重试、回滚与 Smoke Test 各自有明确状态；回滚会创建新的恢复运行。

不要生成灰度流量控制、自动回滚开关或无真实来源的指标图。
```

验收重点：域名与部署对象保持项目范围；技术预览不替代业务状态；恢复语义正确。

## 11. 批次 H：移动端与可访问性

目标 Frame：屏幕目录第 10 节全部移动 Frame。

```text
把已通过的桌面设计适配到 390×844，并为指定移动状态生成独立 Frame。

导航进入抽屉；表格在移动端优先保留对象、状态、问题和下一动作，可把次要证据折叠进详情；表单使用单列；底部动作不能遮挡日志或校验信息。所有触控目标至少 44×44px，焦点顺序与视觉顺序一致，状态不只用颜色表达。

不要创造新的移动视觉语言。继续复用桌面版字体、色彩、边框、圆角、状态标签和数据。
```

## 12. 每批修订提示词

当首轮结果偏离参考时，使用局部修订而非重新生成：

```text
只修改选中的 Frame，不改变已通过的 Shell、令牌和数据。

请逐项修正：
1. [写出可测量差异，例如“表格行高从约 72px 收紧到 56–59px”]
2. [写出层级差异，例如“页面只保留一个蓝色主按钮”]
3. [写出语义差异，例如“blocked 状态补充影响与目标页深链”]

保持 Frame 名、页面状态、项目/版本/发布单/Manifest ID 不变。不得新增未在屏幕目录中的功能。
```

## 13. Stitch 输出验收与交接

每个批次导出或记录以下内容：

- Frame 链接/截图、提示词版本、使用的参考图和生成时间。
- 桌面与规定移动状态的视觉验收结果。
- 组件复用清单：Shell、按钮、状态标签、表格、抽屉、对话框、步骤条、日志查看器。
- 与 [`05-traceability-matrix.md`](./05-traceability-matrix.md) 的差异；任何新增交互必须先回到 PRD 判定，而不是直接进入实现。
- 原型连接：项目目录 → 项目总览 → 发布单 → Gate → 构建 → 测试部署 → 生产审批 → 成功/证据；项目配置、域名和部署记录可从项目内导航直接到达。

最终交付前，逐屏检查裁切、留白、字体、权重、边框、圆角、焦点、错误态、空态和权限态；用相同视口将 V2 参考与 Stitch 结果并排比较，不以“已经生成”作为视觉验收通过。
