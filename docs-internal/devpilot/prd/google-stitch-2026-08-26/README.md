# Devpilot Google Stitch 重设计 PRD 套件

> 版本：1.0；日期：2026-08-26；适用端：桌面 Web 后台，兼顾 390px 移动端降级；目标工具：Google Stitch。

## 1. 交付目的

这套文档用于在 Google Stitch 中重建设计 Devpilot 后台框架和项目模块。它不是脱离产品现状的概念稿，而是把当前工作区的路由、前端状态、API、持久化对象、已通过评审的 V2 视觉方向和仍需新增的目标能力合并成一个可执行设计合同。

本套件回答四个问题：

1. Devpilot 后台的全局壳层、导航、权限和通用交互应该怎样组织；
2. 项目目录、项目接入、项目信息、发布、配置、域名入口和部署证据有哪些完整功能；
3. 每个页面应该呈现哪些字段、状态、动作和下一状态；
4. 怎样把这些约束按批次输入 Stitch，并让不同画板保持一致。

## 2. 文档清单

| 文件 | 用途 |
| --- | --- |
| `01-platform-shell-prd.md` | 后台全局框架、导航、权限、响应式与通用状态 PRD |
| `02-project-module-prd.md` | 项目模块全功能、业务规则、状态机、字段和验收标准 |
| `03-screen-catalog.md` | Stitch 需要生成的页面、弹窗、抽屉和关键状态清单 |
| `04-stitch-playbook.md` | Stitch 建项方式、分批提示词、参考图绑定和设计 QA |
| `05-traceability-matrix.md` | 功能到当前路由、前端源码、API、证据图和目标画板的追溯矩阵 |
| `DESIGN.md` | 可导入 Stitch 的 Devpilot 设计系统和使用理由 |

## 3. 证据优先级

发生冲突时按以下顺序判断：

1. 当前工作区真实代码与 API；
2. `evaluation/design/project-module-v2/` 中已通过领域合同复核的 10 张 V2 设计稿；
3. `project-skills/devpilot-project-workbench-design/` 与 `project-skills/devpilot-product-design-lessons/`；
4. 2026-08-25 当前项目模块 UI/UX 审计；
5. 更早的流程审计和架构文档。

旧页面或旧深链仍可存在，但不能覆盖当前主流程。当前代码已经把发布改为 `/projects/:id/releases` 独立路径；旧 `?view=releases` 和 `?view=deployments` 仅用于重定向兼容。部署记录仍是完整业务能力，但主要通过发布单、DeploymentRun 抽屉和运行详情进入。

## 4. 能力标签

所有需求使用以下标签，避免把目标设计误写成当前已实现能力：

| 标签 | 含义 |
| --- | --- |
| `LIVE` | 当前前端与后端已有可达路径 |
| `API` | 后端已有能力，目标 UI 需要补齐或重组入口 |
| `DESIGN` | 本次 Stitch 目标体验，可由已有数据或前端组合实现 |
| `BACKEND` | 目标体验需要新增服务端读模型、字段或聚合接口 |
| `DEFER` | 明确不进入本轮主流程，禁止在设计中伪装为可用 |

## 5. 核心产品决策

- 平台导航按用户任务分为：仪表盘、项目、基础设施、资源、运维、治理、配置、团队、管理、帮助。
- 项目上下文包含五类业务目的：项目信息、发布、项目配置、域名与入口、部署记录。路由实现可以独立或嵌套，但用户不能丢失这些任务入口。
- 一页只有一个实心主操作；问题修复动作必须紧邻问题。
- 列表默认使用紧凑表格，不用大卡片堆叠。
- 环境在配置页是作用域选择器，不是并排比较卡。
- 发布状态由服务端生命周期、Gate Catalog、Production Preview 和运行证据共同决定，前端不能自行拼接“已通过”。
- 版本切换、升级、恢复都创建受审计的新部署/发布记录，不能直接改写当前指针。
- Manifest、digest、Run ID、输入哈希和原始 JSON 是技术证据，默认进入详情或抽屉。
- 灰度、蓝绿、自动发布、真实流量切换、指标驱动终止和自动回滚 provider 当前不属于已完成能力，设计不得以可用控件呈现。

## 6. Stitch 使用顺序

1. 在 Stitch 建立 Web 项目，导入本目录的 `DESIGN.md`。
2. 上传 `evaluation/design/project-module-v2/references/selected-direction-1-with-header-3.png` 作为整体视觉基准。
3. 上传 V2-01 至 V2-10 作为相应页面和状态的局部参考。
4. 先执行 `04-stitch-playbook.md` 的全局壳层提示词，再按批次生成页面。
5. 每批生成后按 `03-screen-catalog.md` 和 `02-project-module-prd.md` 核对字段、状态和动作。
6. 只有当上一批的壳层、组件和语义稳定后，才继续下一批，避免 Stitch 在不同画板中漂移设计系统。

## 7. 最终验收口径

- 页面覆盖与 `03-screen-catalog.md` 一致；
- 主要字段和动作能在 `05-traceability-matrix.md` 找到真实来源；
- 所有不可执行按钮都有原因和修复出口；
- 所有高风险写操作有确认、幂等和审计语义；
- 1440×1024 桌面稿无横向溢出，390×844 移动稿不压缩表格到不可读；
- 键盘可到达导航、筛选、环境选择、步骤、行操作、弹窗和抽屉；
- 不把未实现能力、内部状态码、API 路径或设计说明放进产品主视觉。
